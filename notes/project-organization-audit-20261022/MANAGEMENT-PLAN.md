# 本地工程与GitHub统一管理实施方案

状态：2026-10-22方案，尚未实施迁移、分支收口、远程同步或自动检查。本文是本轮审计的实施建议，不是另一个项目当前入口。

目标：任何有效成果都有可恢复身份；任何开发者只读一个总入口就知道目标、代码位置、验证边界和下一步；GitHub上的受控版本能在干净目录恢复。本轮不改变平台、功能、音乐行为或PCB接口。

## 1. 权威来源与职责

采用一个内部开发仓库，以internal为共享远程。现有origin/public地址用于独立对外发布流程，不作为内部开发备份目标。internal的私有性须实际核实，不能从名称推断。

工作树共享Git对象库，不能当作多个独立备份。D盘副本也只有在位于独立设备或另有异地副本时才提供相应灾难恢复能力。

| 内容 | 唯一职责 | 维护方式 |
|---|---|---|
| 根README | 全项目首入口，链接project/CURRENT.md和协作规则 | 不重复大段会漂移的资源/验证数字 |
| project/CURRENT.md | 人读导航：目标、有效版本、各领域入口、验证边界、下一步 | 接续66a4已有体系；整合后在main可见 |
| project/state.json | 当前候选/最近板验/开发实验/硬件verified与WIP身份、状态和引用 | 扩展已有结构，避免另建平行登记表 |
| project/catalog.json | 模块及工程文件角色：产品构建、测试、探针、支持、历史 | 保留现有模块目录职责 |
| project/versions/ | 各冻结版本的实际输入清单和哈希 | 源码、hex/vh、约束、顶层、参数、宏、脚本均纳入；不只记录.v |
| project/dependencies.json | 工具版本、环境依赖、安装方法及配置项 | 不把个人机器绝对路径当可移植工程身份 |
| docs/00-协作/AGENT-BOARD.md | 负责人、路径所有权、共享接口及交接 | 写会话稳定ID/分支/实际工作区；不只写“Codex” |
| 本机工作区配置 | 把逻辑版本/分支映射到C盘、D盘实际位置 | 本机绝对路径可不提交，但应有受跟踪模板；不是另一份产品状态 |

所有旧入口保留其版本和日期，通过总入口导航；不擅自把不同验证范围合成一个“当前已验版”。AGENTS必须指向上述入口。已有旧工作树显式读取主项目最新协作规则，接合该规则更新时不覆盖其源码成果。

## 2. 身份与验证必须绑定

每个有效候选至少登记：稳定ID、角色、owner、分支、源提交、源码清单及摘要、顶层与构建profile、工具版本、约束、回归入口、证据清单及哈希、验证状态、禁止/允许的使用范围、最后核对时间。

身份必须区分：

1. 最近板验音乐基线。
2. 频率/重奏等开发候选。
3. 完整功能产品顶层候选；尚不存在时明确写“待实现”。
4. 静音结构探针、关闭子树的面积实验等临时配置。
5. GUI与协议候选。
6. 硬件已核对快照及正在推进的WIP。

验证分别记录行为回归、综合、路由、STA、板验。路由完成和STA通过是不同状态；旧板验不自动覆盖新RTL。临时关闭可视化的实验即使面积/时序通过，也不能升级为完整功能候选。

采用两阶段记录避免自引用：先提交实现得到源提交S，再按S构建并提交结果记录V；V引用S与实际输入哈希。构建若使用脏目录，只能作为开发证据，保留补丁/输入哈希，不标记可发布版本。生成的源清单不把自身或后来生成的日志递归纳入自身哈希。

## 3. 文件与产物分类

先保留现有目录，完成版本保护后再做独立的路径迁移。建议继续用src/rtl、src/constr、src/gowin、src/sim、tools、hardware、experiments，先明确职责即可，不需要立即全部改名。

| 分类 | Git要求 | 位置与限制 |
|---|---|---|
| 源码、静态表、约束、工程配置、工具与测试 | 必须跟踪 | 必须包括构建用.hex/.vh，不依赖别的工作树临时文件 |
| 人工维护的设计、接口契约、状态与清单 | 必须跟踪 | 目录职责固定；跨领域接口改动由对应owner协调 |
| 小型回归/STA摘要、命令、工具版本、输入哈希 | 受跟踪证据目录 | 明确白名单，验证普通git add不会被全局ignore静默排除 |
| 大波形、音频、完整报告、码流 | 有校验的持久归档 | Git保存索引、大小、SHA256、恢复位置与保留规则；不能只写个人绝对路径 |
| 可重生成构建目录、缓存、运行日志 | 不跟踪 | D盘按任务及唯一run ID输出，不覆盖已封存结果 |
| 本机环境、临时会话状态、缓存 | 不当作共同产品状态 | 提供配置模板；不把过期会话ID当可复用工程入口 |

当前fpga-m1-agent-work含开发源码，暂登记为“活跃开发区”，禁止按缓存清理。待负责人提供稳定检查点后，复制受控输入到命名分支的工作区，核对哈希及回归，再切换入口；不移动正在执行构建的目录。原生CAD先按硬件owner提供的稳定快照归档，并核对JSON指针与实际文件一致。

## 4. 分支、同步与合并

- main承载经过审查的集成状态；不代表完整产品已经完成。遵循现有“main由用户合并”规则。
- 一个任务使用一个命名分支和明确owner的工作区。从main或登记的候选源提交起步，记录理由；不要默认旧detached目录就是最新源。
- 已有分支先保存后比较，不直接合并79/81个提交、不删旧分支、不强推历史。
- 收工检查diff，精确选择文件提交；WIP可以提交并上传，但必须标明未验证项，不能用PASS掩盖缺口。
- 完成每个可恢复检查点后，同步对应分支到核实过的internal远程，核对远程实际提交与本地一致。没有上传成功则交接状态明确写“仅本地”。
- internal/public双用途通过显式目标和检查隔离；可在准备好的管理变更中设置默认推送目标和推送检查，但这些本地约束不能替代服务端规则。
- 在仓库权限/套餐允许的条件下设置main保护、禁止强推/删除、要求适当检查与审查；若当前不可用，明确缺口并使用手动检查记录，不能声称已强制执行。
- 对外版本走已有导出/脱敏流程，单独审查后发布，不能直接把内部main推到origin/public。

保存与验收分离：上传WIP解决成果恢复；合并审查解决行为和集成质量。两者都需要，不能等全产品通过才保存开发源码。

## 5. 自动检查与恢复验收

接续已有project_version.py等工具，先审查其当前SCOPE与工程文件解析，补足新实验、硬件和构建配置覆盖；不能把旧工具存在当成新范围已受保护。

最小快速检查应能发现：

- 当前状态引用不存在的分支/提交/清单，或入口路径失效。
- 必需的构建输入未被Git跟踪、被ignore排除、缺失或哈希不符。
- 从.gprj/Tcl解析到外部工作树或个人机器文件的必要输入。
- 源版本与回归/构建/STA报告身份不一致。
- 产品候选误用probe profile，或把未完成路由、负时序裕量当成通过。
- 同一受控版本目录出现未登记的新源、重复模块名或工作区漂移。

本轮具体例子：主项目的project_baseline.py与被引用的main-2026-10-09-v2.json本机存在，但当前main未跟踪它们；4d37中也没有该脚本。入口检查必须在干净克隆执行才能发现这一类问题。

分层验证：轻量检查在每次准备提交/合并时执行；相关行为回归随实现变更执行；完整PnR在RTL、约束或构建profile改变、需要验收资源/时序时运行。纯文档索引变更无需重复PnR。云端可以先跑不依赖厂商工具的检查；Gowin等本地检查要记录执行环境和源身份，不能无条件显示绿色。

恢复演练从internal的明确提交开始，在不借用原工作树的干净位置恢复源码，按索引取回大证据，核验哈希，执行版本检查与相关回归。构建输出写新目录。若此步骤依赖旧目录未提交文件，就未达到“GitHub可恢复”。

## 6. 分阶段落地与验收门槛

| 阶段 | 工作 | 完成标准 |
|---|---|---|
| A：保全 | 给4d37与其他owner的稳定检查点建分支，补齐源/约束/表/脚本；保全06df和M1；核实internal权限及私有性并上传 | 无关键成果仅存在于未跟踪目录；上传的检查点能按身份取回 |
| B：入口 | 接续66a4的project体系，加入新FPGA实验、GUI、硬件verified/WIP与真实工作区；修复根README/AGENTS/协作板引用 | 新agent读README后可确定目标、有效版本、owner、构建和验证边界 |
| C：约束 | 收口ignore与证据规则，升级范围检查和远程同步检查；准备仓库保护配置 | 故意漏一个.hex/约束或指向旧源时检查应失败，正常恢复通过 |
| D：恢复 | 按远程版本干净恢复；回归与必要的新PnR；按身份记录结果 | 无旧工作区隐含依赖；不能以旧产物替代新版本验证 |
| E：整理 | 独立提交目录迁移，再处理模块去重与候选接合 | 路径调整可回退；行为及接口保持；旧证据可定位 |
| F：归档 | 核对owner、源提交、证据和恢复能力后归档不活跃工作树 | 没有活跃引用或未保全成果才归档；不直接删除旧目录 |

本项目当前应先执行A、B。A、B可以在各自owner提供的稳定检查点上推进，不要求停止所有FPGA/硬件工作。涉及main接合和跨领域接口仍遵循现有协作规则。

## 7. 每次交接的固定内容

```text
任务ID / owner / 分支 / 工作区
源提交 / 源清单摘要 / 脏目录情况
做了什么 / 尚未实现或未验证什么
实际执行的回归 / PnR / STA / 板验及各自证据身份
远程上传是否完成 / 远程实际提交
下一步入口 / 当前阻塞 / 谁仍在使用此目录
```

管理完成的判据是：干净恢复可执行，版本状态可解释，远程检查点可取回，新增成果持续按流程归档。新增一个README、推一次main或把目录改整齐，都不能单独满足这些判据。
