# 双段衰减（decay2）落地记录 —— 2026-10-23

## §0 一句话

`osc_env` 的 DEC 段现在支持**先快后慢**两段：电平跌破可编程断点后，右移量从 `d_k`
换成更慢的 `d2_k`。默认关闭（`d2_k=0`），关闭时与改动前**逐位一致**，
所以全部历史音频判据、全部已调好的音色都不受影响。

## §2 三个设计决定（以及为什么不是别的做法）

### 2.1 断点和第二段斜率做成**全局**寄存器，不是每泛音一份

`GENERAL-INSTRUMENT-GAPS-20261022` §4.1 给的方案 B 是
`decay2_tab[64]`（4 槽 × 16 泛音 × 5 位 = 320 bit）+ 新写口。本实现没有走那条，
理由三条：

1. **每泛音一份要在 TDM 流水线里多一个读口。** `osc_env` 在全设计里只有
   **一个实例**，由 `tdm_engine_rh` 分时服务 512 个槽。加表就要在这个
   每拍都在跑的流水线里插一次 BSRAM 读，同步读要 +1 拍 —— 而
   `tdm_engine_rh` 里已经有一大段注释在追"包络与相位差一步"的问题
   （试过两级串联 `osc_env`，实测无效后回退）。在一条已知敏感的流水线上
   加一拍，风险远大于收益。
2. **物理上也说得通。** 真钢琴进入尾音后，能量由共鸣板辐射主导，
   各泛音的衰减速率本来就趋于一致。每泛音独立在**第一段**最有用
   （`d_k` 已经做到了"低次慢、高次快"），第二段统一并不丢东西。
3. **11-04 只剩 12 天。** 全局版是 1 个比较器 + 1 个 mux；每泛音版是
   新表 + 新写口 + 新读口 + 流水线对齐 + 新的上位机协议字段。

**代价如实说**：全局版做不出"第 3 泛音的尾巴比第 5 泛音长"这种细节。
留作后续。

### 2.2 只允许"变慢"，不允许"变快"

```verilog
wire d2_on = (d2_k != 5'd0) && (d2_k > step_k) &&
             !release_phase && (lvl_i < d2_lvl);
```

`d2_k > step_k` 这一条是**安全属性**，不是优化：

`k` 越大步长越小。如果某个泛音原本 `d_k = 20`（已经很慢），配一个
`d2_k = 15` 会让尾音**突然加速** —— 听感上是"尾巴被掐断"，
比没有双段衰减更糟。加上守卫之后，第二段要么更慢、要么完全不生效，
不存在"配置错了反而更差"的分支。

### 2.3 默认关闭，不是遗漏

打开会改变**所有既有音色**的听感。而"与改动前逐位一致"是全部历史
回归判据、全部已调好的参数、全部板上音频证据的前提。

所以：`0x5F = 0x00` 出厂默认，`0x38` 的 `artic_enable=0` 同一个道理。

## §3 寄存器与怎么试听

| 地址 | 字段 | 语义 |
|---|---|---|
| `0x5D` | `D2_LVL` 低字节 | 断点，Q1.15 小端 |
| `0x5E` | `D2_LVL` 高字节 | 同上 |
| `0x5F[4:0]` | `D2_K` | 第二段右移量，**0 = 关闭** |
| `0x5F[7:5]` | 保留 | 写 0 |

**为什么放 0x5D–0x5F**：0x5A/0x5B/0x5C 是"音色形状"一族（SPEC_MODE /
HARM_PADS / TILT），紧邻其后。不放 0x72 是因为那格已被曲谱段占位
（`0x72 保留`，扩曲谱时会撞车）。

### 3.1 推荐起始值（钢琴取向）

```
写 0x5D 0x66      # D2_LVL lo
写 0x5E 0x26      # D2_LVL hi   → 0x2666 = 9830 ≈ 0.30 × 32768
写 0x5F 0x0F      # D2_K = 15   → τ = 2^15 样本 ≈ 0.62 s
```

`k` 与时间常数的关系（`τ ≈ 2^k / m` 个采样，`fs = 52734.375 Hz`）：

| `d2_k` | τ | 到 -60 dB（约 6.9τ） |
|---:|---:|---:|
| 13 | 0.16 s | 1.1 s |
| 14 | 0.31 s | 2.1 s |
| 15 | 0.62 s | 4.3 s |
| 16 | 1.24 s | 8.6 s |
| 17 | 2.49 s | 17 s |

**断点怎么选**：0.25–0.40（`0x2000`–`0x3333`）。太高会让"先快"那段
听不出来，太低则第二段几乎用不上。

### 3.2 板级确认

```
python tools/board_velocity_check.py write 0x5D 0x66
python tools/board_velocity_check.py write 0x5E 0x26
python tools/board_velocity_check.py write 0x5F 0x0F
python tools/board_velocity_check.py dump        # 回读应为 66 26 0F
```

回读值来自 `reg_bank_compact` 的 `mem`，逻辑用的是 `regs_flat`。
两者同源的前提是 `REG_LIVE_MASK` 覆盖了这 3 个字节 —— 已加，
并由 `tools/check_live_mask.py` 静态守住（见 §4.2）。

## §4 验证

### 4.1 仿真判据（10 项，`sim/tb_decay2.v`）

| # | 判据 | 为什么需要它 |
|---|---|---|
| D1 | 关闭时 4000 拍轨迹与"改动前参考实现"逐拍相同 | **最重要的一条**：改错不是"新功能不好用"，是所有音色全变味 |
| D2 | 切换发生在"第一次跌破断点"那一拍，**两侧都验** | 只验一侧会漏掉"断点被改低" |
| D3 | `d2_k < d_k` 时完全不生效 | 守住"尾音不会被掐断" |
| D4 | 第二段单步步长严格小于第一段 | 证明"确实变慢"，不只是"轨迹不同" |
| D5 | 到尾音的拍数 ≥ 1.5× | 可听效果的量化 |
| D6 | 第二段每拍严格下降，不死锁 | 移位被移成 0 会永久卡住 |
| D7 | 释放只由 `r_m/r_k` 决定 | 演奏者的手势不该被音色形状改写 |
| D8 | `d2_lvl=0` 但 `d2_k≠0` 等价关闭 | 半配置不会意外改音色 |
| D9 | `s_lvl` 高于断点 ⇒ DEC 停在 `s_lvl`，第二段不用 | 有延音的音色不该被误伤 |
| D10 | `m=1/2/3` 三档都能正常终止 | 第二段只改 k，不该破坏 m 语义 |

**参考模型是独立手写的**（`legacy_next` 函数），不复用 DUT 任何中间量 ——
复用就失去对照意义。

### 4.2 静态检查

- `tools/check_live_mask.py`：39 个地址活跃，**0 个 DEAD READ**，
  `tb_vel_shape` 的 `LIVE` 常量与 RTL 逐位一致
- `tools/check_boot_contract.py`：**MISMATCH 无**，0x5D–0x5F 归入 BOOT ONLY

### 4.3 反向对照（证明判据有牙）

| 变异 | 应该红 | 实际红 |
|---|---|---|
| NEG1 去掉 `d2_k > step_k` 守卫 | D3 | **D3** ✓ |
| NEG2 断点减半 `d2_lvl >> 1` | D2 | **D2** ✓ |
| NEG3 第二段改用 `step_k - 3`（变快） | D4/D5 | **D4 + D5** ✓ |

**第一轮反向对照有两个漏洞，被自己捅出来了，已修**：

- D3 原来从 `FULL` 起跑、断点 16384，而 `d_k=20` 要 24 万拍才跌破断点，
  测试只跑 3000 拍 ⇒ 第二段从未触发 ⇒ 去掉守卫也照样绿。
  而且 `d_k=20` 时 `(lvl*3)>>20` 恒被钳成 1，与 `d2_k=15` 的步长一样，
  两个因素叠在一起让 D3 完全没有分辨力。
  **修法**：起跑点放到断点下方，并把参数改成 `d_k=15 / d2_k=12`
  （在 lvl=20000 处步长分别是 1 和 14，一眼分得开）。
- D2 原来只验"跌破前没变"，断点被改**低**时当然也没变 ⇒ 照样绿。
  **修法**：加"跌破后 300 拍内必须已经分叉"（正确实现在第 1 拍就分叉，
  断点减半的实现要再走 ~946 拍，300 拍时仍相同）。

**还有一个自己踩的坑**：加完 `osc_env` 端口后第一次跑全回归，`tb_strike` 的
B 组全部报 `steps 40000`。原因是那个 tb 里有个 `osc_env` 参考实例没接新端口，
悬空成 `z` ⇒ 比较变 `x` ⇒ 整个包络算成 `x`。**iverilog 只给警告不报错**。
这条提醒：**给 `osc_env` 加端口时，所有例化点都要检查**，包括 tb。

## §5 面积与时序（实测，`build_decay2_v1` vs `build_strike_v2`）

| 资源 | strike_v2 | decay2_v1 | 增量 |
|---|---:|---:|---:|
| Logic | 12657 (62%) | **12562 (61%)** | **−95** |
| Register | 4280 (28%) | 4302 (28%) | +22 |
| CLS | 8275 (80%) | **8265 (80%)** | **−10** |
| BSRAM | 14 (31%) | **15 (33%)** | **+1** |
| DSP | 10 (42%) | 10 (42%) | 0 |
| setup slack | +11.858 ns | **+11.300 ns** | −0.558 ns |
| hold slack | +0.205 ns | +0.205 ns | 0 |

**怎么读这张表**：

- **Logic / CLS 反而变小了**（−95 / −10）。这不是"功能是负成本"，而是
  改动了组合逻辑之后综合器找到了不同的打包方式。**结论只能是"代价在噪声
  量级内"，不能声称"加功能省了面积"** —— 换一次综合就可能反过来。
- **BSRAM +1 是 `pROM` 从 3 变 4**（`SDPB 8 / SDPX9B 3` 都没变）。这是一次
  综合器推断出来的小 ROM，不是双段衰减功能需要的存储。功能本身只需要
  2 个 16 位寄存器 + 1 个 5 位寄存器 + 1 个比较器 + 1 个 5 位 mux。
- **setup 掉 0.558 ns 是唯一真实的代价**。余量 11.3 ns 对 27 MHz（37 ns 周期）
  仍然是 30% 以上，不构成风险。
- BSRAM 15/46、DSP 10/24、CLS 80%，**都还有充足余量**。

## §6 明确没做

- **每泛音独立的第二段斜率**（方案 B 的 `decay2_tab`）—— 理由见 §2.1
- **第二段独立 `m`** —— 复用第一段的 `d_m`。规格里的 25 位包含 `d2_m`，
  本实现只做了 `d2_k`（`k` 的影响远大于 `m`：`m` 只有 1/2/3 三档）
- **第二段独立 `d2_shift`**（`INSTRUMENT_ENV` 的 tick 分频）—— 只在
  `INSTRUMENT_ENV=1` 时有意义，产品顶层该参数为 0
- **线性衰减模式下的双段** —— `exp_mode=0` 时 `step` 走 `linear_step`，
  `d2_k` 完全不参与。这是对的：双段衰减本来就是"一阶指数的斜率切换"，
  线性模式下没有"斜率"这个概念。产品顶层 `exp_mode` 固定 1。
- **板级验证** —— 板子当前不在线（见 `NIGHT-20261023-VELOCITY.md` 之后的记录）
