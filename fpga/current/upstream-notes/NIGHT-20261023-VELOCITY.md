## 2. 关键设计决定（以及为什么不是别的做法）

### 2.1 力度为什么必须"逐通道"

第一版我给了 `pad_pitch` 一路 4 位力度，取"最近一次按下的那一路"。
**这是错的**，原因在 `pad_pitch` 的工作方式：

- 它是**轮流扫查** 38 个通道（`sc` 计数器），扫到哪个通道与"谁刚按下"无关；
- 从"某通道 state 变 1"到"pad_pitch 扫到它"，最多隔 38 拍，相位不可控。

后果很具体：先按住 A、再按 B 时，A 的 note-on 会拿到 **B 的力度**。
和弦同时按下时三个音力度全一样。这不是精度问题，是**张冠李戴**。

所以改成 `vel_bus[4*i +: 4]`，`pad_pitch` 用 `vel_bus[{sc[3:0],2'b00} +: 4]` 按通道取。
成本：16×4 = 64 个寄存器 + 一份减法/移位 + 下游一个 16:1 的 4 位选择器。

**判据（tb_pad_chain）**：
- `[3]` 通道 1（vel 3）与通道 6（vel 12）同时按下 → 两个事件各自带对的力度；
- `[4]` 先按 A（vel 2）再按 B（vel 14）→ A 的 `ev_vel` 仍是 2。
这两条是单路实现必然失败、逐通道实现必然通过的**判别性**用例。

### 2.2 力度的 0 点为什么是 `hi` 而不是 `base`

能发出音符的前提是 `cnt > hi`（`hi = base + base>>3 + base>>5 ≈ 1.156×base`）。
也就是说 `cnt ∈ [0, hi]` 这一段**物理上永远到不了**。

若以 `base` 为 0 点：`vel = (cnt - base) >> shift`，
则 `vel = 0/1` 这两档永远不可达（`base=500` 时死区 ≈ 78 拍 ≈ 2.4 档）。
力度表最底下 2 档白写。

改成 `vel = (cnt - hi) >> shift`：刚过触控阈值 = vel 0（最弱），越用力越大。
`hi` 本来就在同一个 `always` 块里算好了，**零额外成本**。

### 2.3 力度在"判定按下那一拍"锁存，而不是发事件时现算

`pad_scan` 的事件发射要等 `note_busy`（note_map 装载完），
忙的时候可能等好几轮扫描；那时 `raw/base` 已被后续扫描更新，力度会被"稀释"。

所以在 `S_LAT` 里 `state[i]` 由 0 翻 1 的那一拍就写进 `vel_ch[i]`，
与 `note_busy` 完全解耦。**判据 `[7]`** 专门守这一条：`note_busy` 恒 1 时按下，
力度仍然是 9，不是 0。

### 2.4 `0x6F` 为什么要单独开一格

`vel_shift` 是**必须上板实测才能定**的量：
- 电极面积、覆盖层厚度、内部下拉强度都未知 ⇒ `base` 可能落在 200 也可能落在 3000；
- `base` 小 ⇒ 每档增量小 ⇒ shift 要小；反之要大。

写死在 RTL 里等于把"没测过的数"固化进码流。开一格寄存器（`0x6F`，默认 5），
配合 `0x64/0x65/0x67/0x68` 遥测，可以在**不重新综合**的前提下现场标定。

## 5. 板级验证：根因找到了，而且修好了

### 5.1 先纠正一个我自己踩的坑：波特率

**板子的 UART 不是 115200。** 现在烧在 Flash 里的 `tdm_live_test.fs` 用的是
`UART_BAUD=460800`（`retrigger-20261015-09/source/src/rtl/tdm_live_test.v:9`）。
我在 115200 下探了一整轮，全程静默，白花了时间。

> 产品顶层 `tdm_ship_owned` 用的是 **115200**，两者不同，别混。

### 5.2 板级确认了 `0x6E` 这个 bug

烧 `tdm_live_test.fs`（10-15 验证过的固件），在 **460800** 下：

```
tx 0f6e -> rx 6e00     ← 地址回显 0x6E，数据 0x00
tx 0fab -> rx ab00
tx 0f12 -> rx 1200
```

`0x6E` 读出来是 **0x00**，即 `vel_vscale = 0` = 力度功能**关**。
这是"力度对音色完全无影响"在真实板子上的直接证据。

### 5.3 根因：引脚 87 的复位极性从头到尾就是反的

**这是一整晚最重要的发现，而且它推翻了我上一版文档里的全部猜测。**

用探针码流（`beacon v3`，字节 = `{6'b101010, 慢速计数位, rst_n}`）读出来：

```
0xA8 x19407   0xAA x19385     ← 100% 的帧里 bit0(rst_n) = 0
```

`rst_n` 恒为 0 ⇒ 整片设计被永久按在复位里 ⇒ UART 什么都不发。**这就解释了一切。**

那为什么旧固件用同一根引脚能跑？看它的复位逻辑
（`retrigger-20261015-09/source/src/rtl/tdm_board_test.v:12-16`）：

```verilog
reg [1:0] reset_release;
always @(posedge clk or posedge rst_n) begin
    if (rst_n) reset_release <= 0;                          // 引脚高 ⇒ 一直按住
    else       reset_release <= {reset_release[0], 1'b1};   // 引脚低 ⇒ 两拍后释放
end
... .rst_n(reset_release[1])
```

**这段逻辑是反的**：引脚低，内核才被释放。它能在板上跑，
恰恰证明**这块板子的引脚 87 空闲时就是低电平**。

再查硬件依据 —— Sipeed 官方 20K 例程：

```tcl
IO_LOC "sw0" 87;  IO_PORT "sw0" IO_TYPE=LVCMOS33 PULL_MODE=NONE;
IO_LOC "sw1" 88;  IO_PORT "sw1" IO_TYPE=LVCMOS33 PULL_MODE=NONE;
```

> *"The switches on the 20K are **pulled down** so there's no need for a pull up or
> pull down in the FPGA. The output is a **logic one when you press** the switch."*

⇒ **Tang Nano 20K 的 S1/S2 是「板上外部下拉 + 按下接 3V3」= 高有效。**
项目里所有 cst（`tdm_top.cst` / `tdm_live_test.cst` / `osc_additive_top.cst`）
都按"低有效"处理，全都错了。

这也解释了为什么把 `PULL_MODE` 从 `DOWN` 改成 `UP` 也没救回来：
内部弱上拉打不过板上 10k 下拉，引脚仍然读 0。

### 5.4 修法：不跟按键极性赌，用 POR 保证启动

新增 `engine/src/rst_gen.v`：

```verilog
wire rst_n = por_done & ~btn_stable;    // POR 完成 且 按键没被按住
```

- **POR 计数器**：上电后数 `2^15` 拍（27 MHz 下 1.21 ms）自动释放复位。
  **不管按键接反、断线、被按住，设计都能确定性启动。**
- **按键消抖**：电平需稳定 `2^14` 拍（0.61 ms）才被承认，高有效。
- 刻意选择的失效方向：**极性若与实物不符，最坏后果是"按 S1 不复位"，
  而不是"整机不启动"。**

引脚 87 同时改名 `rst_n` → `btn_rst`（自解释极性），
cst 改 `PULL_MODE=NONE`（板上已有下拉），sdc 的 `set_false_path` 同步改。

### 5.6 第二个坑：我改错了模块 —— 而且回读骗了我

修完复位后 `0x6E` 仍然读 0x00。我第一版的解释是"综合器把 `initial` 丢了"，
**这个解释是错的**，后来查清了真正的原因，而且它比原来的解释严重得多。

#### 5.6.1 `tdm_top_owned` 用的不是 `reg_bank`，是 `reg_bank_compact`

```verilog
// tdm_top_owned.v:388
reg_bank_compact #(.FLAT_MASK(REG_LIVE_MASK)) u_reg ( ... );
```

`reg_bank.v` **在整个产品顶层里一次都没被例化**。我改的
`mem[8'h6E]=8'h80` 打在了一个没人用的模块上。

`reg_bank_compact.v` 的默认值是它自己的一个常量：

```verilog
localparam [1023:0] DEFAULTS = 1024'h1100...0002;
initial mem[g] = DEFAULTS[g*8 +: 8];
```

解码出来：`0x5C=0x70`、`0x7F=0x11`（都在）、`0x6E=0x00`、`0x6F=0x00`（不在）。
**这完美解释了板上实测** —— 不是综合器丢 initial，是我压根没改到那个常量。

#### 5.6.2 更严重：`0x6F` 根本不在 `REG_LIVE_MASK` 里

`reg_bank_compact` 有**两套存储**，作用完全不同：

| 存储 | 服务对象 | 谁能写 |
|---|---|---|
| `mem[0:127]` | **只服务回读**（`rd_data`） | 任何 `addr < 0x80` 的写入 |
| `value` | **只服务逻辑**（`regs_flat`） | **仅当 `FLAT_MASK[g] = 1` 才存在** |

未选中的字节，`regs_flat` 恒为 0。

实测结果：

```
0x6E live? 1     ← 力度灵敏度，通的
0x6F live? 0     ← 力度刻度，死的
```

于是：

```
上位机写 0x6F = 0x05
  → mem 收到 → 回读 0x05 → selftest 全绿
  → 但 regs_flat[0x6F] 恒 0 → r_vel_shift 恒 0
  → vel = (cnt - hi) >> 0，直接钳到 15
  → 力度只有 0 和 15 两档
```

**回读正确 ≠ 配置生效。** 这是比"默认值没写"更难发现的一类 bug：
所有回读判据都是绿的，而实际功能是坏的。

#### 5.6.3 修法与防复发

三处一起改：

1. `REG_LIVE_MASK` 加 `0x6F`：`...000b7801...` → `...000bf801...`
2. `reg_bank_compact.v` 的 `DEFAULTS` 补 `0x6E=0x80`、`0x6F=0x05`
   （同时保留引导序列的写入，双保险：DEFAULTS 保证上电瞬间就对，
   引导序列保证确定性，且不依赖综合器行为）
3. **新增 `0x7D`/`0x7E` 逻辑侧回显**：读它们拿到的是 `regs_flat` 的值，
   而不是 `mem` 的值。上位机因此能区分：
   - 读 `0x6F` 得 `0x05`，读 `0x7D` 也得 `0x05` ⇒ 真生效
   - 读 `0x6F` 得 `0x05`，读 `0x7D` 得 `0x00` ⇒ **写了但逻辑看不见**

两个静态/动态检查固化下来：

- `tools/check_live_mask.py`：抓出所有 `R[8'hXX*8 +: N]` 形式的读取，
  报告哪些地址不在 `REG_LIVE_MASK` 里（DEAD READ）。同时核对
  `tb_vel_shape.v` 里的 `LIVE` 常量与 RTL 逐位一致，防止仿真与实现漂移。
- `tb_vel_shape.v` 的 A5/A6/A7 三条判据：写 `0x6F` 后检查 `regs_flat` 是否跟着变。
  **做过反向对照**：把 `LIVE` 退回旧值，A4/A5 立刻变红，A5 直接打印 "DEAD READ"。

#### 5.6.4 还有一个测试保真度问题（已修）

`tb_vel_shape` 原来例化的是 `reg_bank`，**不是产品在用的 `reg_bank_compact`**。
所以"`0x6E` 默认 `0x80`"这条判据在仿真里绿、在板上却是 `0x00` ——
仿真测的和产品跑的不是同一个模块。

现在两个模块都例化：`u_reg` 是 `reg_bank_compact`（主被测），
`u_ref` 是 `reg_bank`（参考模型，只用来交叉校验默认值是否一致，A4）。

### 5.7 顺手修掉的两个 beacon bug

`uart_beacon.v` 是诊断工具，但它自己有两个 bug，会让探针值不可信：

1. **停止位从来没被驱动**。`bi == 9` 分支只重装移位寄存器、不写 `tx`，
   于是停止位时隙里线上还停在上一个数据位。任何 MSB=0 的字节都**没有停止位**，
   接收方可能把相邻两帧粘在一起。
   （旧测试台用 `0x96`，MSB 恰好是 1，所以"停止位为 1"这条判据被蒙过去了。）
2. **`GAP` 单位是时钟周期，不是位时间**。注释写"空多少个位时间"，
   代码每拍减 1 ⇒ `GAP=200` 实际是 7.4 µs 而不是 1.74 ms。
   板上实测帧率 **12.7 kB/s，超过 115200 8N1 的 11.52 kB/s 上限** ——
   物理上不可能，这就是发现它的线索。

修完后实测帧周期 **1820047 ns**，理论值 `(10+200)×8666.7 = 1820000 ns`，偏差 0.003%。

### 5.8 标定工具的一个量程 bug

`board_velocity_check.py` 原来算 `span = 1023 - hi`，但 **RC 计数器是 12 位（0..4095）**，
所以建议的 `vel_shift` 全部偏小 2~3 档。已修，并加了通道分类：

裸开发板上 40P 排针什么都没接，实测 16 路分成三类：

| 类别 | 通道 | base | 含义 |
|---|---|---|---|
| 未接 | 0-5, 11, 14, 15 | 12~56 | 放电极快，电极没接上 |
| 可用 | 6, 8, 9, 13 | 581~3346 | 落在合理区间 |
| 饱和 | 7, 10, 12 | 4095 | 一直充不满 |

**这不是真实电极板的读数。** 之前工具把这三类平均成 1403 再推 `shift=0`，
是错的；现在会分类、只用可用通道标定，一条都没有就明确说"标不了，别动 0x6F"。
