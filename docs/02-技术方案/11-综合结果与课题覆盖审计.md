# 第二部分　两个问题的诊断（这是本次综合最大的收获）

## 问题 1：正弦表没有进 BSRAM，而是变成了 LUT 逻辑

**证据**：
- 综合日志说 `Extracting RAM for identifier 'sine_tab'`（它试过了）
- 但资源报告里 **BSRAM = 0，SSRAM = 0，ROM16 = 0**
- 而 LUT 用了 2070 个

**根因**：**块 RAM 是同步读的**（地址要先寄存，数据下一拍才出来）。
而我们的代码是**组合读**：

```verilog
assign s_val[g] = sine_tab[ phase[g][23:16] ];   // 异步读 → 无法映射到 BSRAM
```

综合器无法把它放进 BSRAM，只能退化成 LUT 搭的多级选择树。

**代价**：
- 浪费约 1000+ LUT（256×16 的表用 LUT 实现）
- 关键路径上多了 5 级以上的 LUT 延迟（见上面的 `s_val[0]_0_s5126 → ... → s4280`）
- **而这一切本可以用 1 块 BSRAM（16 Kb）解决**

## 问题 2：加法链是组合的，路径太长

**根因**：`sum_comb` 用的是组合 always 块 + for 循环：

```verilog
always @(*) begin
    sum_comb = 0;
    for (k = 0; k < NUM_PARTIALS; k = k + 1)
        sum_comb = sum_comb + (...);
end
```

综合出来是一条**串行的 8 级加法链**（`sum_comb_0 → sum_comb_1 → ... → sum_comb_10`）。

**代价**：单这一条链就贡献了约 13.877 − 8.223 ≈ 5.6 ns。

## 两个问题的修复方向（都很标准）

| 问题 | 修法 | 预期收益 |
|---|---|---|
| 异步读表 | **把表地址寄存一拍，数据下一拍出**（标准 BSRAM 读时序）；用 `reg` 数组 + 同步读写法 | 表进 BSRAM（省 ~1000 LUT），路径短一大截 |
| 组合加法链 | **改成加法树 + 流水线打拍**（每级之间插寄存器） | 路径从 O(N) 降到 O(log N) |
| 额外 | 给 clk 加 `.sdc` 时序约束（现在没有，工具用默认值） | 时序分析才有意义 |

> **这两个修复都不改变算法**，只改"怎么摆硬件"。修好后要重新跑 `verify` 确保仍与 Python 模型逐位一致。

# 第五部分　结论与下一步

## 5.1 这次综合的价值

**它一次性暴露了三件在仿真里看不到的事**：

| 仿真看不出的 | 综合暴露的 |
|---|---|
| 正弦表会不会进 BSRAM | ❌ 没进，变成 LUT 逻辑 |
| 组合加法链会不会超时 | ❌ 违例 −2.987 ns |
| 8 泛音到底占多少资源 | 12% LUT —— 比预期高 |

**这证明了"仿真 + 综合"双轨验证的必要性** —— 而且综合可以**完全离线跑**（本机 CLI 已跑通，不需要板子）。

## 5.2 一个必须修正的认知

之前（审计 v2）我把"全并行上限 ≈ 92 泛音"当作 BSRAM 端口限制来论证 TDM 的必要性。
**综合结果给出了更精确的图景**：

> 当前的**异步读表**写法，连 8 个泛音都没能用上 BSRAM（全变成 LUT）。
> 真实约束不只是"端口数"，更是 **"BSRAM 是同步读的，必须按它的时序写代码"**。

→ **改法明确**：地址寄存一拍 → 数据下一拍出 → 表进 BSRAM。
→ 但这样每个泛音的表读会**多一拍延迟**，8 个泛音若各自独立读表，仍需 4 块 BSRAM（真双端口），**端口约束依然成立**，TDM 的必要性也依然成立。

## 5.3 修复已完成并验证（2026-09-24 当晚）

**结论：两个问题都修好了，而且效果远超预期。**

### 修法

| 问题 | 修法 |
|---|---|
| 异步读表 → 进不了 BSRAM | 表地址寄存一拍、**同步读** |
| 组合加法链 → 路径太长 | 8 路求和改成**加法树 + 逐级打拍**（7 级流水线） |

**算法一字未改** —— 同样的相位累加、同样的表、同样的定点乘移位、同样的饱和。

### 验证：输出样本序列逐位一致

| | v1 | v2 |
|---|---|---|
| 与基准比对样本数 | — | 各 2000 个（两个测试） |
| **不一致样本数** | — | **0** |
| **最大差异** | — | **0** |
| 附加延迟 | — | **6 个样本**（流水线深度，48 kHz 下 125 µs） |

→ **修改的是"怎么摆硬件"，不是"算什么"。** 这正是我们要的结果。

### 综合对比

| 资源 | v1（异步读表+组合加法） | **v2（同步读表+流水线）** | 变化 |
|---|---|---|---|
| **Logic** | 2467 / 20736（12%） | **371 / 20736（2%）** | **↓ 85%** |
| ├ LUT | 2070 | **19** | **↓ 99%** |
| └ ALU | 397 | 352 | ↓ 11% |
| Register | 197 | 391 | ↑（流水线寄存器，正常） |
| **BSRAM** | **0** | **8 / 46（18%）** | **表终于进 BSRAM 了** |
| DSP | 3 / 24 | 3 / 24 | 不变 |
| **SETUP slack** | **−2.987 ns（违例）** | **+4.244 ns（满足）** | **违例已消除** |
| 数据路径 | 18.281 ns | **11.050 ns** | ↓ 40% |

> **LUT 从 2070 降到 19** —— 因为那张 256×16 的正弦表从"LUT 搭的多级选择树"
> 变成了真正的 BSRAM。这是本次修复最大的收益。

### ⚠️ 但修复暴露了一个更硬的约束（重要）

**BSRAM 用了 8 块 —— 8 个泛音，一块一个。**

综合器选择为**每个读端口复制一份表**（而不是用真双端口共享）。

**含义（这直接决定架构路线）**：

| 泛音数 | 预计 BSRAM | 占 46 块 |
|---|---|---|
| 8 | 8 | 18% |
| 16 | 16 | 35% |
| **32** | **32** | **70%** |
| **46** | **46** | **100%（上限）** |
| 64+ | 不可行 | — |

→ **全并行的实际上限是 ≈ 46 个泛音**（不是我之前估的 92）。
→ 我之前的"92"是按**真双端口 2 读/块**算的理论值，但**综合器实际按 1 读/块复制**。
→ **这反而更强地支持了 TDM 的必要性**：要做 128–512 泛音，必须时分复用。

> 补充：理论上可以手工约束成真双端口（2 个泛音共用一块），把上限提到 92。
> 但这需要精确控制综合器的存储器推断，**属于后期优化项**，现在不碰。

### 时序距离 108 MHz 还差多少

| 目标时钟 | 周期 | v2 数据路径 11.050 ns | slack |
|---|---|---|---|
| 工具默认（无 .sdc） | 15.294 ns（≈65 MHz） | 11.050 | **+4.244 ✅** |
| **我们的目标 108 MHz** | **9.259 ns** | 11.050 | **−1.79 ❌ 仍违例** |

→ **还需再优化约 2 ns。** 手段：继续细分流水线（例如把乘幅度那一级拆开）、
   或先把目标降到 54 MHz（18.5 ns，余量充足）。
→ **同时必须补 `.sdc` 时序约束**——现在没有约束，工具用的是默认值，分析没有意义。
