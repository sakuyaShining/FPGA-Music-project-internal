> 2026-10-08 实施更正：每源统一 4 槽；复用前发现并修正 `event_hold` 的连续出队重复/空队幽灵有效缺陷。
> 仲裁修正为空源跳过、只弹出被选源，并给游标加复位；原表达式及清位方式不满足公平性与确认语义。

# 事件通路「静默丢事件」修复方案 v1（待实施）

> 2026-10-07 · 对应目标阶段 2：「输入事件待处理与接收确认，**绝不静默丢 note-off**」
> 配套判据：`src/sim/tb_padfast.v`（门禁 `36 padfast(kf)`，**当前已知失败**）
> 现状基线：`tdm_top.v` blob `6ce64f90649c`；门禁快速门 31/31。

---

## 1. 问题（已实测、已确证根因，不需再论证）

`tdm_top.v` 的**四个**事件源各用**一个单槽挂起寄存器**：

| 源 | 挂起位 | 清位条件 | 锁存判断 |
|---|---|---|---|
| UART(0x61) | `uh_req` | `ev_in_ready` | `if (u_ev_valid)` —— **无判断，会覆盖** |
| 定序器 | `sh_pend` | `ev_in_ready && seq_en` | `if (sq_ev_valid && seq_en && !sh_pend)` |
| 排针 | `dh_pend` | `ev_in_ready` | `if (ev_valid && !dh_pend)` |
| pads | `pp_pend` | `ev_in_ready` | `if (pp_ev_valid && !pp_pend)` |

**缺陷**：挂起位置 1 之后，要等下游事件队列可接收（`ev_in_ready`）才清零。
在这个窗口内到来的事件，因 `!pend` 为假而**被直接忽略** ——
**既不入队、也不报错 ⇒ 静默丢弃**。

**实测（`tb_padfast.v` B 段：松开 pad0 的同一拍按 pad1）**：

| 观测量 | 实测 |
|---|---|
| `pad_ev_valid` 拍数 | 2（两个事件都产生了） |
| `pp_pend` 置 1 次数 | 1 |
| **被挂起位挡掉** | **1** ← 丢在这里 |
| `nm_ev_ack` 增量 | 1 |
| note49 所在组 | **−1**（从未分配） |
| 两个事件间隔 | **1 拍** |

对照：单独按 pad1（不重叠）⇒ 正常。**C 通过而 B 失败 ⇒ 触发条件是「紧邻」。**

**UART 那一行更糟**：`if (u_ev_valid)` **没有 `!uh_req` 判断** ⇒ 在 `uh_req` 尚未被接收时，
新一次写会**直接覆盖** `uh_req_note/uh_vel`，且 `uh_req` 保持 1 ⇒
**旧事件被替换成新事件**（不是丢失，而是**错位**）。这一条**尚未构造判据验证**，但代码显而易见。

---

## 2. 必须遵守的既有约束（此前逐一踩过，注释在 `tdm_top.v:707-711`）

1. **每个源都要有挂起/待处理**：只挂最高优先级那个，同拍的低优先级源仍会丢。
2. **`out_ready` 必须是单拍确认**：不能用 `~nm_busy` 电平
   （`nm_busy` 是状态输出、晚一拍 ⇒ 队列会在空闲窗口被抽干）。
3. **队列输出直接进 `note_map`**：中间不要再插寄存器
   （会把 `ev_valid` 拉成连续两拍为高，`note_map` 遂把同一事件**消费两次**）。
4. **不得重写 TDM 合成内核**（用户三条原则之一）；本方案只动**事件汇合**这一段。
5. **不得按行数拆模块**，要按职责：**事件接收**（本次）/ 声部管理 / 谱展开。

---

## 3. 方案：把「单槽挂起」换成「每源小队列」，mux 改为**队列头部直接仲裁**

### 3.1 为什么不是"把挂起位加深"

单槽挂起是**寄存器**：`pend` 与数据是"一个槽"。
若只把判断从 `!pp_pend` 改掉，就必须同时容纳两个事件的数据 ⇒ 需要两个槽 ⇒
**本质上就是一个小队列**。所以直接复用**已验证的** `event_hold.v`（环形 FIFO、
已注册输出、`in_ready`/`out_valid` 握手、自带 `level`/`overflow` 计数）。

### 3.2 结构（每源一个 `event_hold`，mux 读队头）

```
 pads  ──► event_hold(DEPTH=2) ──┐
 定序器 ──► event_hold(DEPTH=2) ──┤
 排针  ──► event_hold(DEPTH=2) ──┼──► 轮转仲裁(读队头) ──► 事件队列 event_hold(EVQ_DEPTH) ──► note_map
 UART  ──► event_hold(DEPTH=2) ──┘
```

**关键差别**：

- 每个源的事件**先入自己的小队列**，`in_ready` 只要队列未满即为 1
  ⇒ **紧邻两拍的事件都能被收下**（不再有"挂起窗口"）。
- mux 选择时**直接看各源队列的 `out_valid`**（队头数据已寄存，天然稳定）；
  被选中的源在 `ev_in_ready` 那一拍得到 `out_ready=1` ⇒ **只弹出被真正接收的那个**。
- **每个源都必须被"泵"到**：`out_ready = (sel_x && ev_in_ready)`。
  未选中的源 `out_ready=0`，队头数据保持不变 ⇒ 不丢、不乱序。

### 3.3 与旧挂起位的关系

*删除* `uh_pend/uh_req/sh_pend/dh_pend/pp_pend` 及配套的锁存寄存器
（`uh_note/uh_vel/sh_*/dh_*/pp_*_r`），因为**队列本身就是那个"待处理"**。

> ⚠️ 但**去掉挂起位不会让高优先级源占住 mux**：占住 mux 的原因是"源一直把 `valid` 拉高"。
> 现在 `valid` 来自**队列的 `out_valid`**，而队头被消费的那一拍 `out_ready=1`
> ⇒ 队列立刻弹出下一个/变空 ⇒ **不再持续占线**（这正是当初加挂起位要解决的问题，
> 换队列后同样解决，且解决得更彻底）。

### 3.4 UART 的特殊处理（保留其原意）

UART 的写是**一拍脉冲**（`wr_en`），且 `r_note_num` 会被下一次写覆盖。
旧代码为此用 `uh_req_note/uh_vel` 在**写入那一拍**锁存。
改为队列后，**同样必须在写入那一拍入队**：

```verilog
//   u_ev_valid 是 wr 那一拍的单拍脉冲 ⇒ 直接作为队列的 in_valid
//   数据取当拍的 r_note_num / u_ev_vel（此刻有效）
event_hold #(.DEPTH(2), .NB(8), .VB(4)) u_uartq ( ... .in_valid(u_ev_valid), ... );
```

并且**必须给 UART 队列加深**：UART 字节间隔远大于队列深度需求，
但为稳妥用 `DEPTH=4`（UART 是最慢的源，且可能被高优先级源长时间压住）。

### 3.5 仲裁保持轮转

现有 `arb_rr` 轮转逻辑**保持不变**，只是 `arb_x` 的来源从挂起位
改为各队列的 `out_valid`：

```verilog
wire arb_u = uartq_out_valid;
wire arb_s = seqq_out_valid;
wire arb_p = padq_out_valid;
wire arb_d = dhq_out_valid;
```

`sel_*` 表达式一字不改。⇒ **优先级公平性行为不变**，`tb_evmerge` 的轮转判据应仍通过。

### 3.6 ★ 新增：**丢弃必须可观测**（目标里"接收确认"的实质）

现有 `event_hold` 已有 `overflow` 计数（队列满时丢弃的次数）。
把**四个源队列的 `overflow` 汇总**，接到一个只读寄存器（通过已有的寄存器读通路暴露），
使"任何一次丢弃都能被主机读到"，而不是静默。
**这是本方案的验收要件之一**，不是可选项。

## 4. 验收（实施后必须全绿，否则回滚）

| 判据 | 期望变化 | 为什么 |
|---|---|---|
| `36 padfast(kf)` | **FAIL → PASS** | 本次修复的目标；它现在的两条失败断言必须转绿 |
| `17 evloss` | 保持 PASS | 8 键同时按/放全对应（已登记） |
| `18 evmerge` | 保持 PASS | 28 条（排针 12 + 真实 UART 8 + 并存 8）不丢、note-off 14/14、溢出 0 |
| `19 alloc` | 保持 PASS | 分配/回收不因事件时序改变而受影响 |
| `28 legato` | 保持 PASS | L1–L4 的实测结论不应改变 |
| `32 pitchmod` | 保持 PASS | 滑音轨迹逐样本（0/39598）不应改变 |
| `11 tdm` 黄金参考 | 保持 0/2495 | 音频数据路径不动 ⇒ 必须逐位一致 |
| `31 spec sha` | 更新 `tdm_top` blob | 改了 RTL 就要重绑（本轮已建立此纪律） |

**新增判据（本方案要求）**：

- 扩充 `tb_padfast.v` 增加 **D 段：三连事件**（同一拍产生 3 个：
  off48 + on49 + on50 —— 通过分别在拍 N、N+1、N+2 按/放三个键构造），
  验证**队列深度足够**且**顺序正确**（off/on 不得乱序）。
- 新增 **UART 覆盖**用例：连续两次 `0x61` 写（间隔 1 拍），验证**两个音都生效**
  （当前实现会覆盖 ⇒ 这是与 pads 同类的缺陷，预期同样失败/同样被修好）。

## 5. 实施顺序（小步、每步可回滚）

1. 先只改 **pads** 一个源为队列（其余三个保留挂起位）⇒ 跑 `36 padfast`，
   确认目标用例转绿且其它判据不退。
2. 再依次把 **定序器 / 排针 / UART** 改为队列，每改一个复跑 §4 全部判据。
3. 最后加**丢弃可观测**（overflow 汇总寄存器）+ 新增判据。
4. 更新 `34-当前版本规格` 的 blob 表与门禁计数；
   把 `36 padfast(kf)` 从"已知失败"改为**正式判据**（去掉 `(kf)`）。

> **每步都必须复跑**：`11 tdm`（音频逐位）+ `17/18/19/28/32`（事件与分配）。
> 任一步出现非预期失败 ⇒ **立即回滚该步**，不要把失败带进下一步。

## 6. 风险与对策

| 风险 | 对策 |
|---|---|
| 队列输出与旧 mux 的握手不一致 ⇒ **消费两次**（本项目踩过） | 严格遵守约束 3：队列输出**直接**进下一级，中间不插寄存器；`36 padfast` 的断言含"两个事件必须恰好被 ack 2 次"，会立刻抓到 |
| 队列引入延迟 ⇒ `18 evmerge` 的 28 条对不上 | 判据是**逐条比对**而非计数，能抓到；必要时把 `EVQ_DEPTH` 调大 |
| 高优先级源饿死低优先级源（挂起位当初就是为这个加的） | `arb_rr` 轮转保持不动；`18 evmerge` 的"并存 8 条"就是专测这条 |
| 改坏音频路径 | 本方案**完全不碰** `tdm_engine`/合成链；`11 tdm` 逐位 0/2495 是硬门 |

---

## 7. 结论与建议

- **建议实施**，且**分源小步走**（§5），每步用现有 6 条判据兜底。
- **不建议**为了省事把四个源一起改（一旦 `18 evmerge` 挂了，难定位是哪个源）。
- **不建议**只加深 pads 就收工 —— UART 那行 `if (u_ev_valid)` 的**覆盖**问题
  与 pads 的**丢弃**问题同源，只修一个会把同类缺陷留在系统里。
- 本方案**不改任何音频行为**，也不重写内核，符合用户三条原则。
