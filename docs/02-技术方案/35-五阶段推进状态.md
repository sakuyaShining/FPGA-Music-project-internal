### 阶段 2 事件通路修掉的三个真问题（都已进闸口）

### ✅ 本轮新增：滑音（portamento）的首个判据（`26 glide`）

| 判据 | 内容 |
|---|---|
| G1 | `glide_en=0` ⇒ `poff` 恒为 0（门控在**应用处**，不是衰减处） |
| G2 | `glide_step=0` ⇒ 不衰减，初值原样出现在 `poff`（**出货默认行为**） |
| G3/G4 | 正/负方向每样本走 `step`，**耗时精确等于 `ceil(|gq0|/step)`** |
| G5 | 小初值 / 带余数也**精确收敛到 0**（不卡在 ±1）—— 这才是"无残余抖动"的真保证 |
| G6 | 收敛后稳定停在 0 |
| G7 | 关滑音期间 `gq` **仍在衰减**：关→等→再打开不残留旧偏移 |

**逐行核对 RTL 后确认的两条「设计如此」**（第一版判据我照文档写错了，3 项假失败）：
1. **衰减不受 `glide_en` 门控** —— 注释明写"关滑音时也要照常走完，否则残留偏移会永久卡住"；

已有的 `17 evloss` 判据** —— 因为 `17 evloss` 测的是"8 键同时按/放、事件都对应"，
用的是**缓慢、不重叠**的激励，恰好避开了"**释放与按下同一拍**"这个条件。

**下一步（已非常窄，分钟级）**：
- 在 `tb_padseq` 里 dump **事件队列**的入队/出队（`event_hold` 的 `out_valid/out_ready`
  与 `note_map` 的 `ev_valid/ev_ack`），确认 note 49 是**没进队**还是**进了队但被 ack 掉**；
- 重点怀疑**同一拍同时到达 note-off 与 note-on** 时，
  `note_map` 的状态机（`ST_IDLE/ST_ALLOC/ST_LOAD`）一次只处理一个事件，
  而 **ack 的时序**可能把第二个事件"确认"掉却没执行。
  （阶段 2 的工作对象正是这条通路；`event_hold` + 轮转仲裁是为它加的。）

**阶段 3 的结论保持不变**：这不是"回收后未复位"，而是**事件在切换瞬间丢失** ⇒
归入**阶段 2**，**阶段 3 的"释放→回收闭环"仍算通过**（组确实回 FREE 了）。
我上一轮把它归到阶段 3 是**判断过早**，此处更正。

#### 🔴 缺陷已精确定位（2026-10-07 第九轮，判据 `tb_padfast.v`，**11 秒**，已登记 `36 padfast(kf)`）

**结论：pad 通路在"释放与按下紧邻"时会静默丢一个事件，丢的是 note-ON。**

**复现（11 秒，不录音频）**：
```
 A 只按 pad0                     事件数=1  在响组数=1  note48 组=0        ✅
 B 松开 pad0 + 同一拍按 pad1      事件数=2  ack 增量=1  在响组数=0  note49 组=-1  ❌
     [事件] 拍=60697 OFF note=48
     [事件] 拍=60698 ON  note=49     ← **两个事件都产生了**
 C 单独按 pad1（不重叠）           事件数=1  ack 增量=1  在响组数=1  note49 组=0   ✅
```
⇒ **两个事件只隔 1 拍产生，但 `nm_ev_ack` 只确认了 1 次**，note49 从未被分配。
**C 通过而 B 失败** ⇒ 确证触发条件是「**重叠切换**」。

**分级定位（两步排除，都有判据）**：
| 测什么 | 判据 | 结果 |
|---|---|---|
| 事件队列 + `note_map` 本身 | `tb_evseq.v`：直接在外部事件口打**1 拍间隔**的 off→on | ✅ **2 秒通过** |
| pad 通路 → 队列 这一段 | `tb_padfast.v`：走完整 pad_scan/pad_pitch | ❌ **FAIL** |
⇒ **丢失不在队列、也不在 note_map**，而在 **pad 通路到队列之间**
（`tdm_top.v` 的 per-source 挂起位 / 轮转仲裁那一段）。

**为什么逃过了已有的 `17 evloss`**：那条判据用的是「8 键同时按/放、缓慢不重叠」的激励，
**恰好避开了「释放与按下紧邻」这个触发条件**。⇒ 判据覆盖了"量"，没覆盖"时序紧邻"。

**为什么重要（对应目标）**：直指阶段 2 的
「输入事件待处理与接收确认，**绝不静默丢 note-off**」。
实测丢的是 **note-ON** —— 比 note-off 更隐蔽：**note-off 丢了会挂音（听得出），
note-on 丢了只是"不响"（听不出，会被当成演奏失误）**。
这也解释了 `tb_show` 里"新音起音不足"的全部现象：
**新音根本没响，听到的是前一个音的释放尾音**。

**下一步（修它的前提，已很窄）**：
在 `tb_padfast.v` 里 dump 队列的写侧信号（`event_hold` 的 `in_valid/in_ready`、
每一路的挂起位 `pp_pend`/`sh_pend`/`uh_req`/`dh_pend`）与轮转指针 `arb_rr`，
确认：
  (a) 第 2 个事件**没被写进队列**（挂起位/仲裁漏采）——最可能；
  (b) 或写进去了但被 `out_ready` 连拍吞掉。
`tb_padfast` **不录音频**，所以这条迭代是**秒级**（对比 `tb_padseq` 的 446 秒）。

**★ 方法论收获（本轮最实用的一条）**：
把"要录音的复现"（446 秒）换成"**不录音、只测事件与组状态**的复现"（11 秒），
迭代速度提升 **40 倍**，才使得这种逐级排除变得可行。
**以后排查事件类问题，先建立"秒级判据"，不要用音频判据去迭代。**

#### 🎯 根因确证（2026-10-07 第十轮）：**单槽挂起寄存器 `pp_pend` 静默吞掉紧邻事件**

**代码位置**：`src/rtl/tdm_top.v:817`（pads 源的事件锁存）

```verilog
//   pads：同样锁存（锁存后它就不再占着 mux，低优先级源才有机会）
if (pp_ev_valid && !pp_pend) begin      // ★ 单槽挂起：pp_pend=1 时这一拍的事件被直接忽略
    pp_on_r   <= pp_ev_on;
    pp_note_r <= pp_ev_note;
    pp_vel_r  <= pp_ev_vel;
    pp_pend   <= 1'b1;
end
```

`pp_pend` 是**单槽挂起寄存器**：它置 1 之后要等 `ev_in_ready`（事件队列可接收）
才清零。在这个窗口内到来的任何事件，`pp_ev_valid` 虽为 1，却因 `!pp_pend` 为假
而**被直接忽略** —— **既不入队、也不报错**，即**静默丢弃**。

**实测证据**（`tb_padfast.v` B 段：松开 pad0 的同一拍按 pad1）：

| 观测量 | 实测 | 含义 |
|---|---|---|
| `pad_ev_valid` 拍数 | **2** | 两个事件**都产生了** |
| `pp_pend` 置 1 次数 | 1 | 只有第一个被接收 |
| **被挂起位挡掉** | **1** | ← **第二个事件被丢在这里** |
| `nm_ev_ack` 增量 | 1 | 只确认了一个事件 |
| note49 所在组 | **-1** | 从未被分配 |
| 两个事件的间隔 | **1 拍**（拍 60697 OFF / 60698 ON） | 触发条件极窄 |

对照：**单独按 pad1**（不重叠）⇒ 正常分配到组 0。
⇒ 判据 `tb_padfast` 现已把根因写成硬断言：
`B-src-produced-2-valid (2)` ✅ 与 `B-dropped-by-pending-slot (1)` ✅ 均通过，
而 `B-both-events-acked` 与 `B-note49-allocated` 失败。

**影响面**：
- 丢的是 **note-ON** ⇒ 比 note-off **更隐蔽**（note-off 丢了会挂音、听得出；
  note-on 丢了只是"不响"，会被当成演奏失误）。
- 这就是 `tb_show` 里"新音起音不足"的**全部成因**：新音根本没响，
  听到的是前一个音的**释放尾音**。
- **同源风险**：`sh_pend`（定序器）、`uh_req`（UART）、`dh_pend`（排针）
  也是**单槽挂起**，**同样有这个缺陷**，只是尚未逐条构造判据验证。

**默认处置：不擅自修**。理由：
1. 这是**输入事件通路的架构性改动**（单槽挂起 → 每源小队列），
   属于阶段 2 的核心工作对象，且会触及 `tdm_top` 的事件汇合逻辑；
2. 修法有多种（每源 1 深 FIFO / 扩大挂起 / 反压上游），**取舍需要设计决定**；
3. 交付物层面还有一条硬要求要一并满足：
   **任何被丢弃的事件都必须可观测**（计数器/状态位），不允许静默丢弃。
⇒ 已把根因、证据、影响面与修法方向完整写入 `tdm_top.v` 的注释（纯注释改动，
   逻辑未变，门禁依旧全绿），并在判据里固化为**已知失败**登记，
   使这个缺陷**不会被遗忘、也不会被误判为"已修"**。

**若要动手修，必须复跑**：`36 padfast`（目标转绿）、`17 evloss`、`18 evmerge`、
`19 alloc`、`28 legato`、`32 pitchmod`。

#### 📋 修复方案已成文（2026-10-07 第十一轮）：`37-事件通路静默丢失-修复方案v1.md`

由于这是**输入事件通路的架构性改动**（且该路径本项目已踩过三次坑，
约束写在 `tdm_top.v:707-711`），所以**先出方案、再动手**。方案要点：

- **根因归类**：四个源各用**一个单槽挂起寄存器**（`uh_req`/`sh_pend`/`dh_pend`/`pp_pend`），
  置 1 后要等 `ev_in_ready` 才清零；该窗口内到来的事件因 `!pend` 为假被**直接忽略**。
- **★ 本轮新发现（同一族的第二个缺陷）**：UART 那一行是
  ```verilog
  if (u_ev_valid) begin          // ★ 没有 !uh_req 判断
      uh_req      <= 1'b1;
      uh_req_note <= r_note_num; // ← 旧事件尚未被接收时，被新事件**覆盖**
  ```
  即 UART 不是"丢弃"而是**错位**（旧音符被新音符顶掉）。
  已核对源码确认（`tdm_top.v:798`）。⇒ 与小节上面的 pads 缺陷**同源**，
  只修 pads 会把同类缺陷留在系统里。
- **修法**：把四处的"单槽挂起"换成**每源一个小队列**
  （复用**已验证的** `event_hold.v`），mux 改为**读各源队头**；
  `arb_rr` 轮转仲裁**一字不改**（公平性行为不变）。
- **必须一并满足的硬要求**：**任何被丢弃的事件都必须可观测**
  （汇总四个源队列的 `overflow` 到只读寄存器）——
  这正是目标里"待处理与接收确认"的实质，不是可选项。
- **实施顺序**：**分源小步走**（先只改 pads → 复跑 → 再依次改其余三个），
  每步复跑 `11 tdm`（音频逐位）+ `17/18/19/28/32`（事件与分配），
  任一非预期失败**立即回滚该步**。
- **不改音频行为、不重写内核**，符合用户三条原则。
- 新增要求：`tb_padfast` 补 **D 段三连事件**（验队列深度与顺序），
  并新增 **UART 连续两次写**用例（复现"覆盖"缺陷）。
