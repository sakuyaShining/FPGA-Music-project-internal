## 2. 失败模式：不是"资源不够"，是"没地方摆"

26 号的 console.log 记录的是：

```
Running placement......
[30%] Placement Phase 2 completed
Running routing......
[70%] Routing Phase 1 completed
Error: DesRoute failed.
[80%] Routing Phase 2 completed
[90%] Routing Phase 3 completed
ERROR  (PR0004) : There are total 0 unrouted nets
```

关键是 `There are total 0 unrouted nets`：**没有一条线没连上**。DesRoute 在 Phase 1 失败但最终 unrouted 计数为 0，这个组合说明失败不是"容量不足"，而是**100% CLS 占用下打包器没有自由度**——每个 CLS 都塞了两个 Logic，But/SR/CE 等 CLS 内部专用线之间互相挤占，某些配对无法布通。

这条结论直接改变了优化策略：目标不是"把 Logic 降到某个百分比以下"，而是"**给打包器让出空 CLS**"。每腾出一个 CLS，打包器就多一对可换位的 Logic。所以省 Logic 的价值远高于按总数比例算出来的价值。

## 3. 动作 A 的设计

### 3.1 为什么单是"换芯片"就能省

旧渲染器 `u_renderer` 2057 Logic，其中绝大部分花在**逐像素**上：

- `background(x, y)` 是一个 9 位 × 9 位坐标驱动的组合函数，带 20 多个区间比较和一张 14 列宽的字形 ROM 查表；
- `mv_panel_driver` 对每个像素都要走 `PIXEL_GET → HIGH → LOW → ACK` 四态，每帧光是一次 320×240 全屏清屏就是 76800 像素。

RA8875 自带 GRAM 与硬件绘制引擎，把"算每个像素是什么颜色"这件事搬到了屏外。新渲染器只负责**发命令**：

| 画面元素 | 旧 | 新 |
|---|---|---|
| 全屏清屏 | 76800 像素 × 2 字节 | 1 条 MCLR（4 字节） |
| 频谱推子（48 根） | 48 个矩形填满 | 48 条 fill rect（10~16 字节） |
| 波形迹（128 列） | 擦 + 画，每列逐像素 | 256 条 draw line（10~16 字节） |
| 音高尾迹列 | 逐像素 | 最多 39 条 draw line |
| 层级标签带 | 字形 ROM 逐像素 | 4 个 glyph（18 字节），仅在层级掩码变化时 |

### 3.2 已核对的 RA8875 寄存器表

数值从 `Adafruit_RA8875` 驱动器逐条抄录核对（该库是 RA8875 数据手册寄存器集的直译）：

| 符号 | 地址 | 本文用法 |
|---|---|---|
| PWRR | 0x01 | 软复位 / 显示使能（bit7） |
| MRWC | 0x02 | 图形/文本模式数据读写 |
| PCSR | 0x04 | 像素时钟分频 |
| SYSR | 0x10 | 色深 bit2=1 → 16bpp RGB565 |
| HDWR..VPWR | 0x14..0x1F | 水平/垂直时序 |
| HSAW..VEAW | 0x30..0x37 | 活动窗口 |
| MWCR0 | 0x40 | bit7 = 文本模式 |
| CURH/CURV | 0x46..0x49 | 图形光标 |
| FNCR | 0x21 | bit5=1 外部字体，=0 内部 CGROM |
| TextCfg | 0x22 | bit6 = 文本透明背景 |
| TextH/TextV | 0x2A..0x2D | 文本光标 |
| BgCol / FgCol | 0x60..0x62 / 0x63..0x65 | 背景色 / 前景色 |
| DCR | 0x90 | 绘制控制：线 0x80，实心矩形 0xB0 |
| MCLR | 0x8E | 显存清零，0x80 = 启动全窗口 |

两条与实现直接相关的协议事实：

1. **4 线串口由硬件跳线选择**，没有软件寄存器切换接口宽度；不能像旧代码里假设的那样去写某个寄存器。
2. 主机侧帧格式是 `RA8875_CMDWRITE(0x80)` 送寄存器地址、`RA8875_DATAWRITE(0x00)` 送负载。

## 4. 已完成的功能实现

`experiments/renderer_swap_ra8875_20261019/probe/` 下两个新文件，`music_visualizer.v` **一行未改**（端口完全对齐，`wave_start` 也接出去了）：

- `mv_panel_ra8875.v`——命令层。主机推高层 op，展开成 RA8875 寄存器/数据字节对，交给已有的 `mv_spi_byte` 主机发送。带**前景色缓存**：连续同色命令跳过 6 个颜色字节（48 根推子同色时有效）。
- `mv_renderer.v`——新渲染器。FSM 与画面语义保持不变，只把输出换成分层 op。

## 5. 仿真验证

### 5.1 字节级（`tb_ra8875.v`，iverilog）

逐字节比对发出的序列与上表寄存器映射：

| 场景 | 实测字节数 | 期望 | 结果 |
|---|---|---|---|
| 上电初始化 | 48 | 48 | PASS |
| fill rect（新颜色） | 16 | 16 | PASS |
| fill rect（颜色已缓存） | 10 | 10 | PASS |
| draw line | 16 | 16 | PASS |
| 1 个 glyph | 18 | 18 | PASS |

过程中查出并修掉一个真 bug：颜色分量最初写成左对齐（`{col[15:11],3'b000}`），与 Adafruit 的右对齐写法不一致；仿真比对后才改对。**如果只靠肉眼审代码，这个错会一路带到硬件上。**

### 5.2 帧级（`tb_render_frame.v`，iverilog）

单独驱动 `mv_renderer`，用替身代替 FFT 与波形采集，跑满 4 帧：

```
frame 1: bytes=4668 late=0
frame 2: bytes=4528 late=0
frame 3: bytes=4374 late=0
frame 4: bytes=4528 late=0
RESULT: PASS no late frames
```

**结论：新帧状态机能跑完整帧，无迟到帧。**

### 5.3 吞吐账

SCK = 27 MHz / 4 = **6.75 MHz**，每字节 8 位：

| | 每帧字节 | 每帧毫秒 | 20Hz 帧预算(50ms)占用 |
|---|---|---|---|
| 旧 ILI9341 全屏清屏 | 153600 | **182.0** | 364% |
| 新 RA8875 整帧 | 4528 | **5.4** | 10.7% |

> **限定（2026-10-22）**：上表的毫秒数是 **SPI 载荷时间**，只算字节数 ÷ 6.75 MHz，**不含** RA8875 的绘图执行时间、busy 轮询、命令序列开销、擦旧画新，也不含与扫描/按键共享 BUS_SCK 的争用。真实帧率必须上板实测。Codex 在 `06df/notes/2026-10-19-WorkBuddy成果与选型基线核查.md` §7.4 对同一类推导提出了这条批评，此处适用。

**单是一次全屏清屏，旧方案就要花掉 3.6 个帧预算。** 这条不需要跑综合，纯算术就能定性说明动作 A 不只是省 Logic，是把可视化从"不可能达到 20 Hz"变成"只占 10% 预算"。

## 6. 资源探针：实测结果（推翻了 87 号的估计）

同一个目录 `build_swap_v0`，从 `build_nominal_v4` 原样复制 103 个文件，只替换 `mv_renderer.v` 并加入 `mv_panel_ra8875.v`，构建 403 秒。

### 6.1 布线**通过**了

```
Running routing......
[90%] Routing Phase 3 completed
Running timing analysis......
[95%] Timing analysis completed
Placement and routing completed
Bitstream generation completed
```

returncode = 0。**这是项目第一次拿到有效的联合布线结果与码流**。26 号基准（同样的输入、只换回旧渲染器）是 `DesRoute failed` —— 为确认可比性，用旧输入重跑了一次，产出数字与 26 号逐项一致（20478/10760/10357/32/22.75），说明工具链确定，两次构建可直接相减。

### 6.2 资源差额

| 指标 | 基准（ILI9341） | 替换后（RA8875） | 差额 |
|---|---|---|---|
| Logic | 20478 | 19850 | **−628** |
| — LUT | 17334 | 16717 | −617 |
| — ALU | 2280 | 2269 | −11 |
| Register | 10760 | 10713 | −47 |
| CLS | 10357 | 10320 | **−37** |
| BSRAM | 32 | 32 | 0 |
| DSP | 22.75 | 22.75 | 0 |

分级账（综合 XML）把差额定位得非常清楚：

```
joint_timing_top/system/visualizer/u_renderer      -609 logic  -47 reg
joint_timing_top/system/visualizer/u_renderer/u_panel   +120 logic   +6 reg
joint_timing_top/system/visualizer/u_renderer/u_panel/u_spi  +37 logic
```

**旧像素通路共 729 Logic，新命令层共 120 Logic，净 −609。**

### 6.3 87 号的估计是错的，这里给出修正

87 号估计"删 `u_renderer`（2057 Logic）换 RA8875 命令发生器（+400）= **−1657 Logic / −851 CLS**"。实测是 **−628 Logic / −37 CLS**，只有估计值的 38%。

错在哪：2057 是把 `u_renderer` 整棵子树算给了渲染器，但其中 1428 Logic 是**画面内容计算**（波形映射、推子高度、尾迹位），这些与输出方式无关，换芯片省不掉。真正省掉的只有像素通路那 729 Logic。**87 号按模块名切账，没有按"与输出方式是否相关"切账。**

更要紧的是：**CLS 仍然 10320/10368 = 99.5%，几乎没动。** 87 号假设"CLS 是被渲染器顶满的"是错的。

### 6.4 但目标还是达到了，原因和 87 号想的不一样

26 号失败于 `DesRoute failed` + `There are total 0 unrouted nets`。替换后多出 **48 个空 CLS**（基准只有 11 个）。

所以第 2 节的判断成立、87 号的具体归因不成立：**约束从来不是"总容量"，而是"打包器自由度"**。

**2026-10-22 修正（结合 4d37 的独立构建）**：本文原写"48 个空 CLS 才够"，过强。4d37 用另一条改动（字形单元展开，只省 141 Logic）得到 CLS 10346 / 空 22，**同样路由通过**。所以路由通过的边界落在"空 CLS 11～22 个"之间：

| 构建 | Logic | CLS | 空 CLS | 路由 |
|---|---:|---:|---:|---|
| 26 号基准 | 20478 | 10357 | 11 | **FAIL** |
| 4d37 字形展开 | 20338 | 10346 | 22 | PASS |
| 本文 RA8875 替换 | 19850 | 10320 | 48 | PASS |

可复用的判据应当写成：**空 CLS 从 ~11 个抬到 ~20 个以上即可越过路由门槛，与 Logic 总量关系不大**（省 628 Logic 只换来 26 个 CLS，省 141 Logic 换来 11 个）。Logic 百分比不能作为判据。

但要注意：**路由通过不等于可交付。** 两个通过点都测出 setup 违例（本文 −5.608 ns、4d37 −6.397 ns）。真正的瓶颈已从"布不通"转为"时序"。

### 6.5 新暴露出来的真问题：−250.223 ns TNS

布线通过后时序分析第一次跑完，代价是暴露出 26 号从来测不到的违例：

| 项 | 值 |
|---|---|
| core_clk Setup TNS | **−250.223 ns**（127 个端点） |
| 最差路径 Slack | **−5.608 ns** |
| 数据延迟 | 42.110 ns（周期 37.037 ns，超 5.07 ns） |
| Clock Skew | 0.000 ns |
| core_clk Hold TNS | −0.002 ns（1 个端点，可忽略） |
| 分析路径数 | 68913 |

最差路径前十名全部来自同一处：

```
u_tdm/sl1_4_s0/Q  ->  u_tdm/amp2_4_s0/RESET
u_tdm/sl1_4_s0/Q  ->  u_tdm/amp2_10_s0/RESET
u_tdm/sl1_4_s0/Q  ->  u_tdm/phase_mem_..._s/DI[23]
```

即 **TDM 加的槽寄存器 → 幅度寄存器复位端**，是 512 槽合成引擎（`u_tdm` 3999 Logic）里一条 `槽寄存器 → 幅度寄存器` 的控制回馈。这不是布局问题（clock skew 0.000），是拓扑问题：`sl1` 之后串了太长的组合云。

**结论：动作 A 价值确认，但同时把主矛盾从"布不通"推到了"时序违例 5.6 ns"。**

## 7. 已确认的语义差异（必须在硬件上比对）

1. **字体丢了。** 内部 CGROM 是 8×16 ASCII，原 `mv_font.vh` 的自定义字形（含两个中文宽度占位）不再存在，层级标签带要重画。
2. **绘制引擎完成不再轮询。** ER-TFTM070 模块未引出 SDO，所以 `op_done` 是靠时间预算发的，主机可能跑在绘制引擎前面。这是整个替换最大的功能风险。
3. **标签带只显示 4 个。** 原实现在 320 宽度内也只放得下 `char_id 11..14`，新实现同样只发 4 个，没有新增差异。
4. **推子下落的擦除色**用画布背景色代替原来的 `background(x,y)`，网格线区域会有可见差别。
5. 清屏改用 MCLR（约 500 µs），取代旧方案整帧逐像素刷新。

## 8. 下一步（按优先级）

1. **攻 `u_tdm` 的 −5.608 ns。** 这不是本任务引入的，只是此前测不到。切入点看 `u_tdm/u_pmod/command_store` 与 `physical_store` 两个存储块之间有没有可以提前一拍的控制量。
