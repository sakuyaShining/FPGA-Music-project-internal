# 第一部分　修复的 4 个 Bug

## 🔴 Bug 1（致命）：按住音时改参数**完全无效** —— "塑谱"演示是假的

**现象**：
```
修复前：
  前半段（谐波）主要谱峰: ['440', '880', '1320', '1760', ...]
  后半段（应变成钟）主要谱峰: ['440', '880', '1320', '1760', ...]   ← 完全一样
```

**根因**：`Voice.__init__` 里把 `inc`（频率增量）和 `amp`（幅度）**固化了**：
```python
self.inc = np.array([freq_to_inc(f0 * r, fs) for r in ratios], ...)   # 创建时算一次
```
之后改 `state["inharm"]` 只影响**新按下**的音，**正在发声的音一点都不变**。

**为什么这是最要命的**：我在上一轮告诉你"按住 `A` 然后连续按 `.`，会听到音色从管风琴连续变成钟"——
**那句话在当时的代码里是假的**。而这恰好是整个产品概念（"塑谱"）的核心演示。

**修法**：新增 `Voice.set_spectrum(ratios, amps)`，演奏中途可更新频谱：
```python
def apply_to_sounding():          # play 模式里，每次改参数都调用
    rr = make_ratios(state["inharm"])
    aa = make_amps(state["npartials"], state["rolloff"])
    for v in state["voices"]:
        if v.active:
            v.set_spectrum(rr, aa)
```

**修复后验证**：
```
修复后：
  前半段（谐波）: ['440', '880', '1320', '1760', '2200', '2640', '3080']
  后半段（钟声）: ['440', '880', '1215', '1760', '1915', '2640', '2685']
                                      ↑ 1320→1215   ↑ 2200→1915   ↑ 2640→2685
```
第 3/5/7 个泛音精确地移动到了非谐比例上，**音高（440/880/1760/2640）完全不动**。

## 🟠 Bug 2：改幅度会"咔哒"

**现象**：改 `[` `]` `-` `=` 时幅度瞬间跳变，产生咔哒声。

**修法**：幅度用 **10 ms 线性斜坡**过渡（`amp` 当前值 → `amp_t` 目标值）。
频率则**立即生效**（因为相位连续，改频率本身不会咔哒）。

---

## 🟠 Bug 3：方向键会弹出音符

**现象**：按方向键会发声。

**根因**：Windows 下方向键等功能键是**两个字节**，以 `\xe0` 或 `\x00` 打头。
原代码把 `\xe0` 丢掉后，**第二个字节被当成普通字母** —— 例如上箭头是 `H`，而 `H` 在键位表里是 A 音。

**修法**：
```python
if c in (b'\x00', b'\xe0'):
    msvcrt.getch()      # 吃掉第二个字节
    continue
```

---

## 🟠 Bug 4：音频回调里抛异常会让整个流**静默死掉**

**现象**：一旦回调里出异常，声音停止，但程序还在跑，没有任何提示。

**修法**：回调整体 `try/except`，异常记到 `state["err"]`，主循环检测到后打印并退出。

# 第二部分　算法可行性验证

## 2.1 什么叫"算法可行"

本方案的算法 = **加法合成**：N 个完全独立的振荡器，各自有
相位累加器 / 频率 / 幅度包络，求和后饱和限幅。

要判定"可行"，需要四个维度都过：

| 维度 | 说明 |
|---|---|
| **数学正确性** | 频谱是否落在理论位置？非谐结构能否实现？ |
| **数值可行性** | 定点实现会不会溢出、丢精度、产生噪声？ |
| **硬件可行性** | 能不能综合进目标 FPGA？资源与时序够不够？ |
| **音乐可行性** | 听起来是不是乐器？ |

## 2.2 已验证 ✅

| # | 命题 | 证据 | 强度 |
|---|---|---|---|
| 1 | **频谱精确** | 8 个泛音的 FFT 谱峰全部命中，误差 < 1.67 Hz（FFT 分辨率 4.17 Hz，即误差 < 半个格） | **强** |
| 2 | **泛音真正独立** | 只改第 3 个泛音的频率 → **只有第 3 个谱峰移动**，其余 7 个逐位一致 | **强** |
| 3 | **非谐变形可实现** | 1320→1215 Hz、2200→1915 Hz、2640→2685 Hz，音高不动 | **强** |
| 4 | **定点无溢出** | 24 位相位 + 16 位样本 + 8 位幅度，饱和限幅有效；与浮点模型逐位一致 | **强** |
| 5 | **Python 模型 = RTL** | 各 12000 样本比对，**不一致 0、最大差异 0** | **强** |
| 6 | **可综合** | 8 泛音单声部：371 LUT(2%) + 8 BSRAM(18%) + 3 DSP，**SETUP slack +4.244 ns（满足）** | **强** |
| 7 | **可实时改参数** | 频率立即生效（相位连续）、幅度 10 ms 斜坡 | **强**（本次修复后） |
| 8 | **能出声、像乐器** | 3 段 demo（小星星 ×2 + 泛音扫描）渲染成功 | **中**（⚠️ 你还没确认听到） |

## 2.3 尚未验证 ❌

| # | 命题 | 为什么重要 | 何时能验 |
|---|---|---|---|
| 1 | **多声部混音不溢出** | 4 声部 × 8 泛音叠加可能削顶 | 需做混音器后仿真 |
| 2 | **TDM 调度器正确** | 决定能否做到 128–512 泛音 | 需写 TDM 后仿真 |
| 3 | **高泛音数的资源与时序** | 全并行上限约 46 泛音（BSRAM 端口） | 需实测综合 |
| 4 | **108 MHz 时序收敛** | 当前仅满足 ~65 MHz，距目标差 1.79 ns | 需补 .sdc + 优化流水线 |
| 5 | **实际听感** | 我只能渲染 WAV，**听不到** | **需要你确认** |
| 6 | **演奏手感** | 键盘交互不等于真实乐器手感 | 需要你实际弹 |

## 2.4 可行性结论

> **核心算法是成熟的、可靠的、已被逐位验证的。**
> **它不是"研究性"的算法 —— 加法合成是 1970 年代就有的成熟技术**（Synclavier、Kawai K5000 等都是加法合成）。
>
> **所以"算法可行"这一点：成立，且证据充分。**
> **但"可行"和"有竞争力"是两件事** —— 见第三部分。

# 第三部分　竞争力评估（诚实版）

你的判断是："算法比较优秀、比较激进，如果能实现应该挺有竞争力。"
我逐句拆开评估，**有同意的部分，也有必须提醒你的部分**。

## 3.1 "算法比较优秀" —— ⚠️ 需要修正

| 说法 | 评估 |
|---|---|
| 算法本身优秀 | ⚠️ **加法合成不是新算法**，1970 年代就有商用产品。**在"算法创新"这个维度上，我们没有优势** |
| 算法实现优秀 | ✅ **这一点成立** —— 逐位一致的 Python↔RTL 验证、同步读表进 BSRAM、7 级流水线，这些是**扎实的工程** |

**关键提醒**：
> 如果答辩时说"我们用了加法合成"，懂行的评委会问：
> **"加法合成 50 年前就有了，你的新意在哪？"**
>
> **答案不能是"算法"，必须是"交互"** ——
> 即：**把音色的内部结构做成一条可以实时演奏的轴**。
> 这是廉价乐器里**真的没被做过**的事。

## 3.2 "比较激进" —— ✅ 但激进的**不是算法，是工程目标**

| 目标 | 激进程度 | 说明 |
|---|---|---|
| 加法合成 | ❌ 不激进 | 成熟技术 |
| **512 泛音** | ⚠️ 中等 | 资源上可行，但**说服力存疑**（见 3.3） |
| **实时塑谱交互** | ✅ **激进** | 这是真正新的地方 |
| **零外设、纯仿真可验证** | ✅ 激进 | 工程方法上的激进 |
| **< 3 ms 确定性延迟** | ✅ 激进 | CPU 架构上做不到 |

## 3.3 ⚠️ 一个必须警惕的陷阱：**指标高 ≠ 竞争力强**

这是我之前审计里已经指出的问题，现在再强调一次：

> **在"只能靠仿真"的条件下，"512 个振荡器"这句话的说服力很低。**
> 因为它**没有付出任何物理代价** —— 只要在测试台里把参数调大、跑一次长仿真、画个频谱就能"声称"。
> 评委（和懂行的人）会想："**那又怎样？**"

**对比**：
| 做法 | 说服力 |
|---|---|
| "我们的测试模式输出了 512 个独立谱峰" | 中 |
| "这是我们**弹**出来的，只有 32 个泛音，但**能实时变形**" | **高** |

→ **胜负手在"能不能演示"，不在"数字多大"。**

## 3.4 真正的竞争力来源（按重要性排序）

| # | 来源 | 我们目前的状况 |
|---|---|---|
| **1** | **交互设计（实时塑谱）** | ✅ 概念成立，本次修复后才真正能演示 |
| **2** | **完整度 + 可验证性** | ✅ **这是我们的强项** —— 逐位一致验证、FFT 证据、综合报告，一应俱全。命中的正是评审判据里的"专业性" |
| **3** | **FPGA 不可替代性的可测证据** | ⚠️ 有论证（确定性延迟），**但还没做 CPU vs FPGA 对比实验** |
| 4 | 指标（振荡器数 × 采样率） | ⚠️ 目前 8 泛音；扩展需 TDM |
| 5 | 算法创新 | ❌ **没有** |

**结论**：
> **竞争力应该建立在 1、2、3 上，而不是 4、5。**
> 特别是 **2（工程严谨性）** —— 在没有实物的情况下，**一套严谨的验证体系本身就是最能打的作品**。

## 3.5 一条现实的对照

从 1442 件历届获奖作品的定量分析（见 `02-什么才叫好作品`）：

| 事实 | 对我们的含义 |
|---|---|
| 音频类一等率 **17%**，高于全体 13.9% | 方向选得不错 |
| 但历届**没有"电子乐器/合成器"先例** | 无参考可抄，**也没人证明过这条路能拿一等奖** |
| 一等率最高的题材是"**有明确现实价值 + FPGA 不可替代**"（机器人 34%、医疗 25%） | **我们的"应用价值"叙事目前偏弱** |
| **26% 的一等奖作品名含具体应用场景词** | 我们需要一个更清楚的"这东西给谁用" |

→ **一个尚未回答的问题**：这台乐器**给谁用、解决什么问题**？
   "给声音设计师做实时音色雕塑"是当前最站得住的答案，但**还没有被验证过**。

# 第四部分　结论与建议

1. **Bug 修好了**（4 个，其中一个直接摧毁核心演示）

## 4.2 建议的下一步（按优先级）

| # | 动作 | 为什么 |
|---|---|---|
| **1** | **你先听一遍修复后的音频**，确认能听到、并且听得出"管风琴→钟"的变化 | 不然我们连"能不能演示"都不知道 |
