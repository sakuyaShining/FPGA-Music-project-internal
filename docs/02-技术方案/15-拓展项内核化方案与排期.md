# 拓展项「内核化」方案与两天排期

> 2026-10-02 · 问题：**能不能在内核（RTL）设计层面把拓展要求全部收下？**
> 答案：**E1–E5、E7 可以完整收下；E6 只能收下 LED 指引那一半；E8 只能收下 FPGA 侧的一半。**
> 本文给出逐项做法、验收证据形式、估时与排期，并如实标出"内核收不下"的部分。

---

## 一、总表（先看结论）

| # | 拓展要求 | 内核能否收下 | 内核侧要做的事 | 证据形式 | 估时 |
|---|---|---|---|---|---|
| **E1** | 复音≥32 / 单音分量≥32 | ✅ **已收下** | 无需再改（32 组 × 16 泛音 = 512 时隙） | **32/32 路基频逐个精确** + 综合 | 已完成 |
| **E2** | ≥3 维表情调控 | ✅ **已收下（运行时可写）** | 颤音深度/速率、滑音时间、开关全部改成寄存器 | 写寄存器 → 频偏 0/26.3/52.6 音分；τ 比值 8.19 | ✅ 完成 |
| **E3** | ≥2 音色自由切换 | ✅ **已收下** | `PRESET` 寄存器 + 引脚/寄存器可选 | 4 个预设 **16/16** 泛音幅度逐个精确 | ✅ 完成 |
| **E4** | 混响 / 延迟 / 合唱 | ⚠️ **延迟 + 合唱已收下**；混响待做 | 一条 4096 样本线缓冲 + 分时双抽头 + LFO 调制抽头；并联湿声支路 + 零延迟旁路 | **冲激响应**：回声间距/幅度逐个精确；合唱延迟在 1024±64 三角起伏 | 延迟+合唱 ✅ 完成；混响 1 天 |
| **E5** | 延迟≤5 ms 且确定性无抖动 | ✅ **已收下（实测）** | 逐拍测量音符事件 → I2S 位；抖动 0 由"晶振直连＋全整数分频＋静态时分调度"结构性保证 | **2807 拍 = 0.104 ms**，对 5 ms **48×** 余量；相位依赖闭式可预测 | ✅ 完成 |
| **E6** | 可视化（LED 指引/李萨如/频谱/波形） | ⚠️ **LED 指引已收下**；图形未做 | `song_seq` 输出拍点+音高编号 → `led[5:0]`（顺手修了共阳极极性 bug） | LED 指引序列 vs 曲谱；集成起音/收音计数 | LED ✅ 完成；LCD 1–1.5 天 |
| **E7** | 脱机 LED 曲目指引 | ✅ **已收下** | 片上曲目定序器（曲谱 `case` 表 + Q24 节拍累加器 + note-on/off 事件）→ 同时驱动 note_map 与 LED 指引 | 音符事件时间戳 vs 曲谱**逐条精确**；速度比 10.00；集成 8 起音/7 收音 | ✅ 完成 |
| **E8** | 蓝牙 + 手机 App | ❌ **内核只能收下 FPGA 侧一半** | UART 协议（已有 rx，需加 tx）＋曲谱下载缓冲＋演奏录音回传缓冲 | 协议回环：下载的曲谱被定序器演奏；录制的事件能回读 | 0.5–1 天 |

**两句话总结**：
1. **纯算法/数据通路类**（E1/E2/E3/E4/E5/E7）——内核完全可以收下，而且**全都不需要开发板**。
2. **需要外部件或人机介面**（E6 的图形显示、E8 的蓝牙与手机 App）——内核收不下；
   E6 的 LED 部分与 E8 的 FPGA 侧协议可以收下，但**不等于该项达成**。

## 二、逐项做法（关键设计点）

### E2 + E3：参数寄存器化 + 音色切换（同一件事）
- 复用全并行版已有的 `reg_bank.v`（256×8）与 `uart_rx.v`（115200 8N1，两字节一帧），搬进 `tdm_top`。
- 引脚有官方来源：`uart_rx=70`、`uart_tx=69`（Tang Nano 20K，BL616 USB-serial）。
  `tdm_top.cst` 里已把这两行注释保留，接口一建好即可启用。
- 需要新增的地址：`vib_on / vib_rate / vib_depth / glide_on / glide_m / glide_k / preset`。
- 现在这些参数是**编译期常量**（与包络参数一致）：`pitch_mod` 的 `LFO_INC/VIB_DEPTH/GLIDE_M/GLIDE_K`
  与引擎的 `GLIDE_EN/VIB_EN` 要改成端口。**改动面小且集中**（`pitch_mod` + 引擎参数 + 顶层接线）。
- ★ 顺带收获：这条 UART/寄存器通路**正是必须项 M1/M9（交互层）要用的地基**。

### E4：效果器（听感提升最大的一项）
- 结构（遵守纪律 D2：干声最短）：
  ```
  合成和 →┬─→ 干声 ─────────────┐
          └─→ 延迟/合唱/混响 ──→ 湿声增益 ─┴─→ 饱和 → I2S
  ```
- **资源**：BSRAM 现用 9/46 → 还有 37 块（每块约 18 Kbit）。
  - 延迟 100 ms @**52734.375** ≈ **5273** 样本 × 16 位 ≈ 84 Kbit ≈ 5 块（按每块 18 Kbit 折算；
  工具实际分配更细，以 PnR 报告为准）
  > ★ 2026-10-02 更正：原文按旧的 46875 Hz 算（4688 样本）。采样率已改，
 > 见 。测试模式频率栅格也随之整体上移
  > （inc 常量没动：225 Hz + slot×27.7 Hz）。
  - 合唱 2 条 20–35 ms 调制抽头 ≈ 2–3 块
  - Schroeder 混响（4 梳状 30–60 ms + 2 全通）≈ 8–12 块
  - 合计约 15–20 块 → **放得下**，但要注意 BSRAM 的读口数与地址计算的关键路径。
- **无板验收**：冲激响应。喂一个单位脉冲，量：回声出现时刻（延迟时间）、幅度比（湿/干）、
  混响 T60、是否溢出/回绕。全部是数值断言，可写成脚本判据。
- **风险**：当前 HOLD slack 只有 **+0.205 ns** → 加逻辑前先确认时序；必要时把抽头地址流水化。

### E5：延迟的"确定性"证明
- 时间账（@27 MHz，1 拍 = 37.037 ns）：
  ```
  控制事件 → note_map 装载 16–32 拍
           → 待生效到样本边界 ≤576 拍
           → 引擎流水线 4 拍
           → I2S 帧 32 拍
           ≈ 最多 650 拍 ≈ 24 µs
  ```
- **抖动 = 0 是结构性的**：全整数分频（27 MHz/18/32）、静态时分调度、无仲裁/无软核。
  这不是"测出来很小"，而是"不可能抖动"——报告里这句比数字更有分量。
- 真正的大头（按键去抖、传感器采样、USB 往返）在**交互层/板子**，要在交付时单独算。

### E6：LED 可以，图形要争引脚
- **LED 指引**：板载 6 个 LED（`led[5:0]`，共阳低电平）。
  可做：① 在奏声部数（已有）② 节拍闪 ③ 测试模式全亮 ④ 曲目指引（E7 的"该按哪个键"）。
-**图形显示**：项目里已有 9K 的 LCD 资产（/ `video_timing.v` / ，
  480×272 RGB，且 20K 也有官方 RGB LCD 例程，`tdm_top.cst` 的排针引脚就是从它抄的）。
  - **冲突**：40-pin 排针 18 根里，音符事件接口已占 16 根 —— 上 LCD 就必须重排引脚，
    而这与 M1（交互层用哪些引脚）是同一个决策。
  - 内核侧可先做且**可仿真验证**：视频时序 + 波形/李萨如绘制引擎，
    把帧缓冲 dump 成 PNG 直接看画对没有（无板可验）。
  - **诚实结论**：不接线就不算 E6 达成，只能说"设计已就绪、仿真已验证"。

### E7：脱机曲目指引（顺便解决现场风险）
- 一个片上定序器：音符 ROM（音高/时刻/时值/音色）+ 小节与节拍计数。
- 收益有两层：
  1. E7 本身（加分项）；
  2. **答辩现场的兜底**：传感器/交互层万一现场出问题，**脱机演示**至少能演完整曲目。
- 验收：dump 音符事件与 LED 的时间戳，与曲谱逐拍比对。

### E8：只做 FPGA 侧
- 可做：UART 收发协议、"曲谱下载"（手机发的音符序列写入曲目 RAM → 与 E7 定序器合流）、
  "演奏录音回传"（演奏事件写环形缓冲，按请求回传）。
- **收不下**：BLE 模块（BL616 需固件）与手机 App（在线曲谱/键位自定义/录音回传界面）。

| 时段 | 任务 | 产出 |

| 第 1 天上半 | **E5 延迟测量**：仿真里量"音符事件→I2S 位"拍数 + 抖动论证 | 一张确定的延迟拍数表 |

| 第 2 天上半 | **E4 延迟 + 合唱**（并联湿声支路） | 冲激响应判据（延迟时间/湿干比/无溢出） |

## 四、必须如实说明的三件事

1. **拓展项全收下也替代不了基础 1（M1/M9）**。
   「自研演奏交互形态 + ≥2 个独立可控维度」目前仍是 **0%**，而它是**必须项**——
   缺它按现状"不合格"，再多加分项也补不回来。
   **好消息**：E2/E3 的寄存器+UART 通路、E7 的定序器、E6 的 LED 指引，
   正是交互层要用的地基 —— 这两天的工作**不是**和 M1 抢时间，而是替它铺路。

2. **E6 与 E8 存在"内核收不下"的硬边界**，报告里不要写成已达成：
   - E6：图形显示要 LCD 接线上板，且与交互层争引脚；
   - E8：BLE 模块与手机 App 不在 FPGA 内。

3. **无板证据的边界**：延迟实测、真实发声、抖动（示波器）、传感器手感 —— 这些必须上板。
   内核侧能做的是把**能在仿真里证明的全部证明掉**（本项目地板阶段就是这么做的）。

## 五、风险

| 风险 | 影响 | 应对 |
|---|---|---|
| **HOLD slack 仅 +0.205 ns** | 加效果器逻辑可能违例 | 加逻辑前先跑 PnR；抽头地址流水化 |
| ~~Logic 72%，E4 预算被吃~~ | ✅**已解决**：滑音改线性速率后**45%**（回收 5591 LUT） | 见 |
| **★ 已发现的隐藏 bug（已修）** | 周期(576) > 时隙数(512) 时前 64 个时隙每样本推进两次 | 时钟链 ÷16 → 周期 = 512 = NSLOT；**这条现在是不变量** |
| BSRAM 余量（37 块）看着多，但混响吃 8–12 块 | 混响可能放不下或挤掉别的 | 先做延迟+合唱；混响用较短梳状（30 ms） |
| 参数寄存器化会碰 `pitch_mod`/引擎端口 | 可能影响已通过的回归 | 每次改完必跑：R0（0/2495）+ 128 档 + 512 档三套 |
| E6 引脚与 M1 冲突 | 交互层方案被锁死 | LCD 与交互层的引脚一起定，别分两次 |
| 拓展项做多了、必须项没动 | 时间分配失衡 | 每完成一项就跑一次覆盖清单，盯住 M1/M9 |
