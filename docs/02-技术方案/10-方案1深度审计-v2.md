# 第零部分　本次仿真证明了什么（新证据）

在审计之前，先跑了一条**纯仿真的完整验证链**，证明这条路走得通：

```
Python 生成正弦表+激励  →  Verilog 仿真  →  dump 12000 样本  →  FFT 验证 + 渲染 WAV
```

**设计**：`src/rtl/osc_additive.v` —— 8 个**独立相位累加器**的加法合成振荡器组
**测试台**：`src/sim/tb_osc_additive.v` —— 两个用例
**工具**：`tools/scripts/additive_tool.py`
**产物**：桌面 `FPGA仿真结果_20260923/`（含 2 个可播放 WAV + 报告 + 频谱 CSV + VCD）

## 实测结果

| 测试 | 期望 8 个泛音 | 实测 | 匹配 |
|---|---|---|---|
| A 纯谐波 | 220 / 440 / 660 / 880 / 1100 / 1320 / 1540 / 1760 Hz | 220.8 / 441.7 / 658.3 / 879.2 / 1100.0 / 1320.8 / 1541.7 / 1758.3 | **8/8** |
| B 非谐波 | 220 / 440 / **607.2** / 880 / 1100 / 1320 / 1540 / 1760 Hz | 220.8 / 441.7 / **608.3** / 879.2 / 1100.0 / 1320.8 / 1541.7 / 1758.3 | **8/8** |

## 这次仿真证明了四件事（都是硬证据）

| # | 证明 | 为什么重要 |
|---|---|---|
| **1** | **每个泛音有独立的相位累加器与频率控制** | A→B 只改了第 3 个泛音的比例（3.00× → 2.76×），**只有第 3 个峰移动**（660→607 Hz），其余 7 个峰位置**逐位一致**。这正面命中赛题对"独立振荡器"的定义 |
| **2** | **频差在 1.67 Hz 以内**（FFT bin = 4.17 Hz，即误差 < 半个 bin） | 频率精度达标，且误差来源是 FFT 分辨率而非设计 |
| **3** | **不碰任何硬件就能听到声音** | 仿真样本 → WAV，这是"只能靠仿真"条件下**保住了听觉反馈闭环** |
| **4** | **非谐变形可实现** | 从纯谐波（管风琴）到含 2.76× 的非谐列（钟），这正是方案1"区别于滤波器"的核心论证 |

→ **结论：方案1的合成引擎部分，100% 可以在仿真里完成并验证。**

# 第一部分　新约束的冲击分析

## 1.1 约束的三层含义

| 约束 | 字面 | 实际影响 |
|---|---|---|
| 没有那么多外设 | 没有传感器、电极、喇叭、杜邦线等 | **方案1的 24 电极输入层无法搭建** |
| 板子不一定一直有 | 硬件访问不稳定 | **依赖上板验证的设计不可行** |
| 只能靠仿真 | 仿真成为主要验证手段 | **"可仿真性"必须成为设计判据** |

## 1.2 什么能仿真，什么不能（关键清单）

| 设计要素 | 仿真能验证吗 | 说明 |
|---|---|---|
| RTL 逻辑正确性 | ✅ **完全能** | 本次已证明 |
| DSP 算法（频谱、包络、混音） | ✅ **完全能** | 本次已证明（FFT 验证） |
| 音频质量（THD / SNR） | ✅ 能 | 从仿真样本计算 |
| 频率精度 | ✅ 能 | 本次已证明 |
| **逻辑延迟**（周期数） | ✅ 能 | 精确到时钟周期 |
| 资源占用 | ✅ 能 | 综合报告（本机已跑通 CLI 综合） |
| 时序收敛（WNS） | ✅ 能 | 静态时序分析，**不需要上板** |
| **加法合成 / TDM 调度正确性** | ✅ 能 | 仿真里所有内部信号可见，**比上板更易调试** |
| **电容传感的物理可靠性** | ❌ **不能** | 这是模拟/物理问题，仿真只能验证其**数字逻辑** |
| 实际音频输出质量（DAC+功放） | ❌ 不能 | 依赖 MAX98357A 与喇叭 |
| 现场演示稳定性 | ❌ 不能 | 接触不良、温漂、干扰 |
| 演奏手感 | ❌ 不能 | 必须真人上手 |

**关键发现**：**除了"物理 I/O"这一小块，方案1的绝大部分都是可仿真的。**
被砍掉的不是"设计"，而是"传感器可靠性验证"和"听觉输出链路"。

## 1.3 一个反向的正面影响（容易被忽略）

原方案1把 TDM 的**调试成本**列为重要代价：
> "出问题时你看到的是'时隙里的数据流'，比全并行的'一眼一条线'抽象得多"

**但在纯仿真环境里，这个代价大幅下降** —— 因为你可以：
- dump 任意内部信号（本次已 dump 整条数据通路）
- 逐周期追踪
- 用 Python 后处理任意中间量

→ **TDM 的最大缺点（不可观测）在仿真里几乎消失。**

**但同时出现一个新代价 → 见第三部分。**

# 第二部分　四个弱主张的逐条裁决

> 方案1在结尾自陈了四条"很可能是错的"主张。现在逐条审。

## 弱主张 1：**TDM 必要且可实现**

### 原文论证
全并行时每个泛音需要每采样周期读一次正弦表；BSRAM 每块最多 2 个读端口；46 块 → 92 端口 → **全并行上限 ≈ 92 泛音** → 512 泛音必须 TDM。

### 裁决：**技术上成立，但"必要性"取决于目标；且遗漏了一个新判据**

| 子命题 | 裁决 | 说明 |
|---|---|---|
| "全并行上限 ≈ 92 泛音" | ✅ **成立** | BSRAM 端口约束是硬事实（UG285 已确认真双端口） |
| "所以 512 泛音必须 TDM" | ⚠️ **逻辑成立但前提可疑** | 前提是"必须做 512 泛音"。而 §弱主张4 会质疑这个前提 |
| "TDM 可实现" | ✅ **成立且比原判断更容易** | 仿真环境下 TDM 可观测性极好 |

### ⚠️ 但发现一个**原方案完全遗漏的新判据：仿真成本**

这是本次审计最重要的新发现：

| 设计规模 | 每样本运算量 | 12000 样本仿真耗时（估） | 迭代体验 |
|---|---|---|---|
| 8 泛音（本次实测） | 8 | **数十秒** | ✅ 舒适 |
| 32 泛音 | 32 | 约 2–4 分钟 | ⚠️ 尚可 |
| 128 泛音 | 128 | 约 10–20 分钟 | ❌ 痛苦 |
| **512 泛音** | **512** | **约 40–90 分钟** | ❌ **不可接受** |

> 估算依据：本次 8 泛音 × 12000 样本的仿真实测在数十秒量级；iverilog 是解释型仿真器，大致线性放大。

**这意味着**：
> 在"只能靠仿真"的条件下，**设计规模本身受仿真速度约束**。
> 一个 512 泛音的架构，每改一行代码就要等一小时才能看到结果 —— 这会摧毁迭代节奏。

**修订后的建议**：
- **开发期用 16–32 泛音**（仿真秒级到分钟级）
- 架构上参数化，**最终验证时才切到大配置**（跑一次长仿真出数据即可）
- 把"仿真时长"写进设计约束，和 LUT/BSRAM 并列

### 弱主张 1 最终裁决
> **部分成立。** TDM 在 >92 泛音时确实必要，且仿真环境降低了它的调试代价；
> 但"必须做到 512 泛音"这个前提本身可疑，而**仿真成本这一新判据会压低开发期的合理规模**。

---

## 弱主张 2：**电容传感可靠**

### 原文判断
"风险中高"，并已列出传感器稳定性、环境漂移、现场翻车等风险。

### 裁决：**❌ 不成立（在当前条件下）**

三重打击：

| # | 打击 | 说明 |
|---|---|---|
| 1 | **没有外设** | 24 片铜箔电极、电阻、连线 —— 用户明确说没有 |
| 2 | **无法验证可靠性** | 传感可靠性是**物理/模拟问题**。仿真只能验证其下游的数字逻辑（计时计数、基线跟踪、事件状态机），**无法验证"手指按上去真的能测出来"** |
| 3 | **原方案已把它放在关键路径上** | 方案1的整个产品概念（5 个维度、双手分工）**全部依赖这 24 个电极** |

**结论**：这一条**不只是"不确定"，而是"当前无法推进"**。
方案1若照原样执行，**第一步就会卡死在输入层**。

### 修订方向（三选一，见第四部分）
- **A**：把输入层降级为"可选的硬件增强"，先用**板载按键 + UART** 满足交互要求
- **B**：先用**行为模型**仿真传感逻辑，硬件传感留到"有板子有器件时再说"
- **C**：重新定义交互——只保留**不依赖任何模拟传感**的输入（按键、编码器、UART）

---

## 弱主张 3：**47 天够用**

### 原文判断
保守估算 44–49 天，成功率 40–50%。

### 裁决：**⚠️ 需重估；天数已变为 41 天；净影响接近中性但结构改变**

**时间账更新**：

| 项 | 原估算 | 修正 |
|---|---|---|
| 基准 | 47 天 | **41 天**（9/23 → 11/4） |
| 硬件 bring-up | 含在内 | **省掉**（无法上板时） |
| 传感器搭建与调试 | 5 小时手工 + 数天调试 | **省掉**（做不了） |
| 演示准备 | 含在内 | **变难**（没有实物，视频只能靠仿真画面） |
| 仿真迭代等待 | 未计入 | **新增**（规模越大越痛） |
| 引擎开发 | 含在内 | 不变 |

**净判断**：省下的时间与新增的困难大致抵消，**仍然偏紧**。

**但有一个结构性变化**：
> 原计划的风险是"硬件调不通"；现在的风险变成 **"做出来的东西看不见摸不着"**。
> 前者是技术风险，后者是**交付风险** —— 后者更危险，因为它直接影响评分。

### 弱主张 3 最终裁决
> **仍偏紧，且风险性质改变**：从"技术做不出来"变成"做出来了但无法令人信服"。
> **必须立刻定义 MVP，并且 MVP 的定义要包含"如何让人相信它工作"。**

---

## 弱主张 4：**32 声部有意义**

### 原文判断
"从产品角度 8–16 声部就够；从比赛角度 E1 明写 ≥32"

### 裁决：**❌ 基本不成立（作为目标）**

三条理由：

| # | 理由 |
|---|---|
| 1 | **音乐上确实过剩** —— 原方案自己也承认了。超过 16 声部不会让音乐更好听，只会让混音更难 |
| 2 | **在仿真环境里，"高数量"变得廉价** —— 因为不需要真的做出硬件，只要在测试台里把参数调大、跑一次长仿真、画个频谱，就能"声称"512 泛音。**这种声称的说服力很低**，评委（和懂行的人）会觉得"那又怎样" |
| 3 | **它消耗的是最稀缺的资源：仿真时间与注意力** |

**关键反转**：
> 方案1原本把"高振荡器数"当作与赛题指标同向的免费收益。
> 但在纯仿真条件下，**这个收益的说服力被削弱了**：
> 因为**没有任何物理约束在抵抗它** —— 512 个振荡器在仿真里和在综合后是不是都能跑，是两码事。

### 弱主张 4 最终裁决
> **基本不成立。** 建议把"声部数"从**目标**降为**参数**；
> 把"**音色表现力 + 可验证的工程严谨性**"提为首要目标。

## 四条弱主张裁决汇总

| # | 弱主张 | 裁决 | 一句话 |
|---|---|---|---|
| 1 | TDM 必要且可实现 | ⚠️ **部分成立** | 技术成立，但"必须 512 泛音"的前提可疑；**新增"仿真成本"判据** |
| 2 | 电容传感可靠 | ❌ **不成立** | 无外设、无法验证、却在关键路径上 → **第一步就卡死** |
| 3 | 47 天够用 | ⚠️ **需重估** | 剩 41 天，风险从"做不出来"变成"做出来没人信" |

**总体**：四条里 **两条不成立、两条部分成立**。方案1的**合成引擎**站得住，**交互层与规模目标**需要结构性修订。

# 第三部分　设计空间重审

## 3.1 新判据：加入"可仿真性"

原方案1的决策判据是"三道闸"（合规指标 / 完整演示 / 报告复现）。
现在必须加**第四道闸**：

| 闸 | 问题 |
|---|---|
| 闸4 **可仿真性** | 这个东西能不能在仿真里被验证？**一轮仿真要多久？** |

**闸4 的三个子问**：
1. **可观测吗**？—— 出问题时能不能 dump 到内部信号？
2. **确定性吗**？—— 同样的输入必得同样的输出？（模拟量、亚稳态、竞争 → 不确定）
3. **仿真成本多大**？—— 一轮多久？迭代一次要等多久？

## 3.2 按闸4 给设计要素打分

| 设计要素 | 可观测 | 确定性 | 仿真成本 | 闸4 结论 |
|---|---|---|---|---|
| 相位累加器 / 波表 | ✅ | ✅ | 低 | ✅ 优 |
| ADSR 包络 | ✅ | ✅ | 低 | ✅ 优 |
| 混音 / 饱和 | ✅ | ✅ | 低 | ✅ 优 |
| 延迟线 / 混响 | ✅ | ✅ | 中（BRAM 建模慢） | ✅ 良 |
| **TDM 调度器** | ✅ | ✅ | **高（随泛音数线性放大）** | ⚠️ 可用但规模受限 |
| **电容传感逻辑** | ✅ | ✅ | 低 | ✅ 逻辑可仿真，**但物理层不可验证** |
| I2S 发送器 | ✅ | ✅ | 低 | ✅ 优 |
| **HDMI / 视频** | ✅ | ✅ | **高** | ⚠️ 无帧缓存时逻辑复杂，仿真慢 |
| WS2812 | ✅ | ✅ | 低 | ✅ 优 |

## 3.3 设计空间里的新选项

### 选项 α：**引擎纯仿真优先，交互后置**

```
Phase 1-2（现在 → 约 10 天）：全部在仿真里做合成引擎
                            └─ 交付：可听的 WAV + 频谱 + 资源报告
Phase 3+（视硬件情况）：   才接交互
```

**优点**：完全不依赖硬件就能产出**可验证的实质成果**
**风险**：如果最终没有硬件，作品缺"实物演示"

### 选项 β：**板载资源做最小交互（零外部器件）**

Tang Nano 20K 自带：
| 资源 | 数量 | 能做什么 |
|---|---|---|
| 用户按键 | 2 | 触发 / 切换 |
| 单色 LED | 6 | 状态 / 简易频谱 |
| WS2812 | 1 | 彩色指示 |
| **UART（经 BL616）** | 1 | **PC 发任意命令 → 无限个"虚拟维度"** |

→ **2 按键 + UART = 零外部器件的最小控制面**，能满足赛题"≥2 个独立可控维度"
**关键**：UART 让 PC 变成**输入设备**（不是计算设备，不违反"PC 不承担核心计算"原则）

### 选项 γ：**行为模型仿真传感，硬件留作增强**

写一个**传感行为模型**（模拟手指接近的电容变化 → 时间计数），
用它驱动事件状态机，验证整条交互逻辑；**物理电极留到有器件时再接**。

**优点**：交互逻辑（防抖、插值、事件识别）全部可验证
**风险**：物理可靠性仍然是未知数

### 选项 δ：**降低规模目标，提高音色表现力**

放弃"512 泛音"，改为 **16 泛音 × 8 声部 = 128**，把省下的仿真时间投入：
- 更精细的泛音级包络
- 非谐变形算法
- 效果器质量

**优点**：仿真快、可迭代、音乐性更好
**代价**：指标（振荡器数 × 采样率）会低约 4 倍

## 3.4 四个选项的对比

| | α 引擎优先 | β 板载最小交互 | γ 行为模型 | δ 降规模 |
|---|---|---|---|---|
| 依赖硬件 | **零** | 需板子 | **零** | **零** |
| 需要外设 | 无 | **无** | 无 | 无 |
| 仿真成本 | 低 | 低 | 低 | **最低** |
| 赛题合规 | 部分（缺交互） | **完整** | 完整 | 完整 |
| 交付说服力 | 中（纯音频） | **高（有实物）** | 中 | 中高 |
| 风险 | 缺实物 | 板子不稳定 | 物理未知 | 指标低 |

**他们不互斥** —— 建议组合：**α + γ 打底（不依赖硬件），β 作为有板子时的部署目标，δ 控制规模。**

# 第四部分　修订后的架构建议（方案1'）

## 4.1 核心转变：三层解耦

把方案1的**整块**设计，拆成**三层独立可验证**的结构：

```
┌─────────────────────────────────────────────────────────────┐
│ 第 3 层  物理传感（可替换、可缺席、不在关键路径）              │
│   现状：缺席                                                │
│   部署目标：板载 2 按键 + UART（零外部器件）                  │
│   可选增强：电容电极阵列（有器件时）                          │
└────────────────────────┬────────────────────────────────────┘
                         │ 统一的「演奏事件接口」（稳定不变）
                         │   NOTE_ON(note,velocity) / NOTE_OFF / SPECTRAL_AXIS / ...
┌────────────────────────▼────────────────────────────────────┐
│ 第 2 层  事件解释与映射（纯逻辑，✅ 完全可仿真）              │
│   基线跟踪 / 插值 / 事件状态机 / 声部分配 / 泛音预算          │
│   → 用【行为模型】驱动，验证全部逻辑正确性                    │
└────────────────────────┬────────────────────────────────────┘
                         │
┌────────────────────────▼────────────────────────────────────┐
│ 第 1 层  合成引擎（✅ 完全可仿真，本次已证明）                │
│   加法合成 / 包络 / 混音 / 效果器                            │
│   → 仿真 dump → FFT 验证 → 渲染 WAV（可以听）                │
└─────────────────────────────────────────────────────────────┘
```

**关键设计决定**：**「演奏事件接口」是三层之间唯一的契约**。
只要它不变，第 3 层怎么换（按键/UART/电容/手势）都不影响第 1、2 层。

## 4.2 参数化规模策略（应对仿真成本）

| 用途 | 泛音数 | 声部数 | 仿真耗时目标 |
|---|---|---|---|
| **日常开发/调试** | 8–16 | 4–8 | < 1 分钟 |
| **功能验证** | 32 | 16 | 数分钟 |
| **最终演示/指标** | 64–128 | 16–32 | 一次性长跑（可接受） |

→ 用 `parameter` 一套代码覆盖三档，**不为了指标牺牲迭代速度**。

## 4.3 交付物形态的调整（关键！）

纯仿真条件下，"作品"是什么？建议改成**三件套**：

| 交付物 | 形式 | 说服力 |
|---|---|---|
| **1. 可听音频** | 仿真渲染的 WAV（多段：谐波/非谐/和声/效果） | 中高 |
| **2. 可视化证据** | 频谱图 + 波形图 + **泛音独立性对比图** | **高**（本次的 A/B 对比就是样板） |
| **3. 工程严谨性** | RTL + 测试套件 + 资源/时序报告 + 一键回归 | **高**（最能体现"专业性"判据） |

**第 3 件被严重低估**：
在"没有实物"的情况下，**一套严谨的验证体系本身就是最能打的作品** ——
它直接命中评审判据里的 **"专业性"** 与 **"完整度"**。

## 4.4 必须先补的一件事

**如果最终要参赛，必须至少让硬件响过一次。**
理由：初赛提交的视频，如果是纯仿真画面，说服力会明显低于"实物发声"。

→ 这是一个**必须尽早验证的可行性问题**：
- 板子什么时候能用？
- 有没有喇叭/耳机？
- 能不能稳定访问？

## 5.1 时间重排（剩 41 天）

| 阶段 | 原计划 | 修订建议 | 变化 |
|---|---|---|---|
| Phase 0 架构验证 | 4 天（含传感 PoC） | **1 天**（传感 PoC 取消，改为"引擎参数化范围确定"） | 省 3 天 |

| Phase 2 单声部多泛音 | 6 天 | **5 天**（仿真验证） | — |
| Phase 3 复音 | 6 天 | **6 天**（TDM 在仿真里更好调） | — |
| **Phase 4 交互** | 6 天 | **改为"事件层 + 行为模型"4 天**；物理传感另计 | 省 2 天 |
| Phase 5 效果+可视化 | 5 天 | **5 天**（可视化改为"仿真出图"而非 LED） | — |

## 5.2 新增风险

| # | 风险 | 概率 | 影响 | 对策 |
|---|---|---|---|---|
| **R21** | **无实物，初赛视频说服力不足** | 高 | **高** | ① 尽早确认板子可用性；② 即使只用一次，也要录"实物发声"；③ 用严谨的验证体系补强 |
