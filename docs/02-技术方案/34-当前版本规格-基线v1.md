## 1. 这一版是什么

一台 **32 复音 × 16 泛音的加法合成电子乐器引擎**，全 FPGA HDL、逐样本实时生成，
经 I²S 输出到 DAC；有 38 通道电容触摸面板作为演奏输入（面板硬件尚在验证中）。

| 项 | 值 |
|---|---|
| 目标器件 | GW2AR-LV18QN88C8/I7（Tang Nano 20K） |
| 采样率 | **46875 Hz**（27 MHz ÷ 576；`BckDiv=16` ⇒ BCK 1.6875 MHz，BCK/LRCK=32） |
| 复音 | **32 组**（`NSLOT=512`，每组 16 个时隙 = 16 泛音） |
| 合成方式 | 加法合成（每泛音独立相位累加器 + 频率调控 + 包络） |
| 输出 | I2S（Philips 标准）→ MAX98357A；24 位内部、取高 16 位送 DAC |
| 控制 | UART 寄存器协议 v1.0（19 号文档 + 修正案 A1–A9）；另接触摸面板 |

## 3. 关键契约（这一版**定死**的行为）

### 3.1 音符归属与抢占（`note_map.v`）

| 动作 | 规则 |
|---|---|
| note-on | 优先级 = **同音重触发 > 空闲组 > round-robin 抢占** |
| 空闲判定 | `gtab[n] == FREE`（127） |
| note-off | 找在奏该音的组，写 `gate=0`（进入释放段，**不是硬停**） |
| ⚠️ **已知缺陷** | **note-off 只清 `gact`，不把 `gtab` 写回 `FREE`** ⇒ 32 组填满后空闲搜索永不命中，之后全部走抢占。**列在阶段 3**（见 33 复核记录二） |

### 3.2 事件接收（2026-10-08 修订）

UART `0x61`、定序器、pads、排针分别有 4 槽 FIFO；中央 FIFO 默认 4 槽。
源输入每个有效时钟表示一个事件，字段在该沿采样。各源保持 FIFO 顺序；
跨源按轮转游标扫描，跳过空源，仅真正接收的源出队。已收下的定序器事件
在关闭 `seq_en` 后仍排空；关闭期间新定序器脉冲不接收。

- **容量保证**：源队列空时，该源可接收连续 4 拍的突发，即使下游完全阻塞。
  已有积压时只保证剩余槽位；不能把中央空槽算作每个源独占容量。
- **持续速率**：取决于 `note_map` 服务和多源竞争；普通满泛音 note-on 接收间隔
  为 20 拍（ALLOC/GLIDE/GQ/16×LOAD），四源持续竞争时每源约每 80 拍一条。
  谱形刷新会延长等待，因此 20/80 拍不是含刷新的最坏延迟保证。
- **超出容量**：丢弃新事件，16 位计数饱和于 `0xFFFF`，复位清零。
  既有 UART 两字节回读通过 `0x0F` 请求，下表均只读，写入忽略：

| 地址 | 值 |
|---|---|
| `0x74/0x75` | UART 丢弃数，低字节/高字节 |
| `0x76/0x77` | 定序器丢弃数，低字节/高字节 |
| `0x78/0x79` | pads 丢弃数，低字节/高字节 |
| `0x7A/0x7B` | 排针丢弃数，低字节/高字节 |
| `0x7C` | 非零状态：bit0 UART、bit1 定序器、bit2 pads、bit3 排针、bit4 中央 FIFO |

读取 16 位活动计数时使用高—低—高读取，高字节不一致则重试。
只读覆盖在 UART 回读处完成，`R` 参数扁平总线不承担诊断镜像。
中央生产者持有队头并用 `ready` 门控有效位，普通背压不会误计成丢弃。
`event_hold` 泛用单元的 overflow 则计 `in_valid && !in_ready` 的拍数；
对于保持 valid 的合规生产者，这表示阻塞拍数，不代表丢失事件。

**保证范围**：容量内不丢失、不错序、不重复；容量外可诊断。
源端没有 ready 输入，因此有限队列不能承诺任意输入速率永不丢事件。

#### ⚠️ (a) 的实测更正（2026-10-07，判据 `src/sim/tb_legato.v` / 门禁 `28 legato`）

**原文写「✅ 已实现且可运行时开关」不准确。** 实测结论是：**机制存在，但在正常演奏下不会被触发。**

根因（逐行核对源码）：

```
glide_ok = GLIDE_EN && !match_r && !free_r        // note_map.v
  · GLIDE_EN 在 tdm_top.v 被**硬接 1'b1**（所以这个门永远为真）
  · free_r  = 被选中的组在【写入前】gtab == FREE
分配器搜索顺序：同音 > FREE > 可回收(!gact) > 抢占
  ⇒ 只要还有空闲组，必然先命中 FREE 档 ⇒ free_r = 1 ⇒ glide_ok = 0 ⇒ **无滑音**
```

实测（L1）：**按住 note60 不放、再按 note64** ⇒ note64 落在**另一个组**（组 1），
未复用 note60 的组 ⇒ **没有滑音**。

**那什么时候才会滑？** L4 实测：把 **32 组全部占满**后再按第 33 个音，
此时才走【抢占】档，被抢的那个组写入前 `gtab != FREE` ⇒ `glide_ok = 1` ⇒ 滑音。

⇒ 也就是说，触发条件是「**声部耗尽**」，而不是文档写的「**上一个音还在响**」。
前者是**分配器的副作用**，后者才是**音乐语义**上的 legato。两者是错位的。

**顺带确认的一条**（阶段 3 修复的正面副作用）：note-off 现在立刻把 `gtab` 写回 `FREE`
⇒「`gtab!=FREE` 且 `gact==0`」的组数**恒为 0**（判据 `29 inv` 全程实测）
⇒ 已松手的组不会残留旧音身份 ⇒ **不可能**产生"由复用引起的意外滑音"。

**待裁定（尚未决定，故本版如实标注为"不触发"而非"已实现"）**：
legato 应由什么触发？
- (A) 保持现状（只在声部耗尽时滑）
- (B) 由「上一个音是否还在响」驱动 —— 需输入层/声部管理提供该信息，并新增 legato 模式位；
  **这是符合"明确区分 legato 与滑动"的做法**，但要动声部分配语义
- (C) 明确降级为"待输入层接入"，本版记为未实现

**在裁定之前，本版把 (a) 视为"未生效"**，不要按"已实现"去写依赖它的判据或交互逻辑。
