## 0. 一句话总结

仿真能证明的东西止于：**数字时序、逻辑等价、资源与时序收敛** ✓。
它**完全不知道**引脚接到什么、电极的物理电容是多少、板上有哪些器件在驱动这些线 ✗。
本项目的三个新特性（pads / 塑谱 / 串行事件）里，**风险最大的是 pads 的 RC 触摸感应** ✗✗，
其次是**顶层端口的引脚分配** ✗（已发现并修掉，见 §2）。

| # | 风险 | 严重度 | 现状 |
|---|---|---|---|
| 1 | **RC 触摸的绝对量程**（内部下拉电阻未知 + 电极电容未知） | ⚠️⚠️⚠️ **高** | 仿真里"手指"是我设定的任意数（30→95 拍）✗ |

## 1. ⚠️⚠️⚠️ RC 触摸感应的绝对量程（**上板第一件要量的事**）

**原理**：RTL 把电极推高 64 拍充电 → 切高阻（内部下拉）→ 数"放电到读 0"的拍数。
放电时间 = R × C，其中：
- **R = Gowin 内部下拉电阻** —— 数据手册**不给典型值** ✗（经验 50~200 kΩ ✗）
- **C = 电极 + 走线电容** —— 取决于**你用什么做电极、走多长线** ✗✗（几 pF ~ 几十 pF ✗）

**为什么仿真测不出** ✗：我在 tb 里把"手指"建模成 `disch_time` 30 → 95 拍 ✗ ——
这个数是**我拍的**，不是从物理推出来的 ✓。仿真只证明了"计数变大 ⇒ 状态翻转"这条**相对关系** ✓，
**完全没有证明真实 RC 会落进 12 位计数器的量程里** ✗✗。

**上板会怎样的两种失败**：
1. **放电太快**（R×C ≈ 1~3 拍 ✗）⇒ 手指带来的增量淹没在 1 拍量化噪声里 ✗ ⇒ 触摸**不可靠** ✗；
2. **放电太慢**（R×C > 4095 拍 ✗）⇒ 计数器**封顶** ⇒ 无论摸不摸都是 4095 ✗ ⇒ **永远摸不着** ✗✗。

**缓解（建议直接照做）**：
- 每根电极**外接 1 MΩ 下拉 + 22 pF 到地** ✓ ⇒ RC = 22 µs ≈ **594 拍** ✓ 落在量程中段 ✓；
  手指再加 ~10 pF ⇒ +270 拍 ✓ ⇒ 增量 ~45%，**远超 15% 阈值** ✓✓；
- 电极用**铜箔/覆铜板**且**引线尽量短** ✓（引线电容是基线的主要不确定项 ✗）。

**可证伪的判据（上板第一步，必须做）**：
> 读回 `pad_raw0` 与 `pad_base0`（见 §2 的读回通道），要求：
> ① 松手时 `raw0 ∈ [20, 2000]`（既没快到底、也没封顶）✓
> ② 手指按下时 `raw0 ≥ 1.3 × base0` ✓
> ③ 连续摸放 20 次，判据 ① ② 每次成立 ✓
> **任一条不成立 ⇒ 先调外接 R/C，再谈演示** ✗（不要在这之前上板调试音乐的其它部分 ✓）

✅ **遥测读回已实现（2026-10-03）**：主机可通过 `0x66 PAD_SEL` 选择通道，再按 A3 读回
`0x64/0x65 PAD_BASE`、`0x67/0x68 PAD_RAW` 和 `0x69/0x6A PAD_ST`。对应实现与仿真证据见
`未验证与挂账清单.md`「⑤ 电极遥测寄存器完成」及 `src/rtl/tdm_top.v`。
因此上板可直接测量，不需要另做调试版；**物理 RC 量程仍未验证**，此项只有连上板和电极后才能关闭。

## 2. ✅ 已修：顶层测试口被自动分配到随机引脚（"电脑能跑上板跑不了"的活标本）

**现象**：`ev_*` / `preset` / `test_mode` 是**测试/调试口** ✓（A6：不上引脚 ✓），
但它们仍是 `tdm_top` 的顶层输入 ✗ ⇒ PnR 把它们**自动分配到板上随机物理引脚** ✗。
实测（③ 完成后那次 PnR，`impl/pnr/tdm_synth.pin.html`）：
```
ev_valid→84  ev_on→82  ev_note[0]→52  [1]→49  [2]→48  [3]→26  [4]→83  [5]→25  [6]→63
ev_vel[0]→10 [1]→86    [2]→85         [3]→11
preset[0]→13 preset[1]→53   test_mode→57
```
**为什么仿真测不出** ✗：仿真里没有"引脚"这个概念 ✓；`pad`/`ev_*` 我只是接一根线 ✓。
**上板会怎样** ✗✗：若上述任何一根在板上被别的器件**驱动为高** ✗ ⇒ `ev_valid`/`ev_on` 读到 1
⇒ **幽灵音符事件**（凭空发声 / 乱响）✗✗，而且**极难查** ✗（看起来像"引擎自己乱跑" ✗）。

**修法（已实施 ✓）**：新增出货顶层包装 **`src/rtl/tdm_ship.v`** ✓
—— 它在 RTL 里把 `ev_*`/`preset`/`test_mode` **接成常量** ✓ ⇒ 这些端口**根本不进网表** ✓✓。
- 工程文件（`.gprj`）不支持 Verilog 宏定义 ✗ ⇒ 用包装模块而不是 `ifdef` ✓；
- **19 个测试台仍然例化 `tdm_top`** ✓ 一行都不用改 ✓（它们要的就是这些口 ✓）；
- cst 里对应的 `IO_PORT` 行已删除 ✓ —— 删之前 Gowin 报
  `CT1135: Can't find object named 'ev_note[0]'` ✗ **正是包装生效的反证** ✓✓；
- `cst_audit.py` 的 A4 判据同步收紧为"这些名字**完全不应出现**在 cst 里" ✓（PS6 = PASS ✓）。

**判据（可自动化 ✓）**：重新 PnR 后检查 `tdm_synth.pin.html` **不含** `ev_*`/`preset`/`test_mode` ✓，
且自动分配引脚数为 0 ✓（所有引脚都显式约束 ✓）。

## 2b. ✗✗✗ 已修：**清一次中间产物就编不出码流**（"电脑能跑"的另一种形态）

**现象**：为了修 §2 的顶层端口问题，我清掉 `impl\` 重新 PnR ✗ ⇒ 直接报
```
ERROR (PR2017): 'dac_din' cannot be placed according to constraint,
                for the location is a dedicated pin (SSPI)
ERROR (PR2028): The constrained location is useless in current package
```
**根因**：`dac_din/dac_ws/dac_bck` 用的引脚 **54/55/56 是本封装的 SSPI（从机配置）专用脚** ✗。
必须让 Gowin 把它们当普通 IO ✓ —— 而 `tools/scripts/build_gowin.ps1` **本来就有这个开关**
（`-SspiAsGpio` → `set_option -use_sspi_as_gpio 1` ✓），它的注释里甚至写着**一模一样的报错** ✓。

**为什么"电脑上一直能跑"** ✗：之前的构建都是**增量**的 ✗ —— 工具复用了历史上那次合法的布点 ✓，
**从来没有重新校验过引脚** ✗。一旦 `impl\` 被清掉（换台机器、git clone、清理目录 ✓）
⇒ 干净构建**立刻失败** ✗✗ ⇒ **根本没有码流可以上板** ✗。

**教训（与 §2 同类，但更隐蔽）**：
> "在我这台电脑上能编过"**不等于**"这个工程能被重新构建" ✗。
> 判据：**把 `impl\` 删掉再编一次** ✓，能出 `.fs` 才算真的可构建 ✓。

**修法（已实施 ✓）**：
- 所有构建命令**一律带 `-SspiAsGpio`** ✓（已写进 `交接-DeepSeek会话恢复.md` 的命令块 ✓，防遗忘 ✓）；
- 把那次**成功构建的 `device.cfg`** 存档到 `src/constr/device.cfg` ✓（`SSPI regular_io = true` ✓），
  作为"工作配置"的记录 ✓（真正的开关走脚本参数 ✓）。

## 2c. ✅ 已根因定位：**16 路三态电极让设计布不通**（C0 的真相）

**症状**：清掉 `impl\` 做干净构建 ⇒ `PR0004`（默认选项报 "0 unrouted nets" ✗ —— 那是工具没真跑 ✗）；
换 `-PlaceOpt 2 -RouteOpt 2` 才看到真相：**`73 unrouted nets`** ✗✗ ⇒ **不生成 `.fs`** ✗。

**定位过程**（每一步都留下可复查的输出）：
1. **环境试金石** ✓：同板同器件的极简工程 `osc_additive_synth` 清 `impl\` 后**干净构建成功** ✓
   ⇒ **工具/环境没问题** ✗ —— 问题在本设计 ✓；
2. 排除：SSPI 专用脚（**已用 `-SspiAsGpio` 修掉** ✓）／`inout` 上的 `DRIVE=8` ✗／
   `spec_ram` 的 `initial` 块 ✗／pad 的 `PULL_MODE=DOWN` ✗；
3. 把 `pad` 从 `inout` 改成纯 `input`（**清掉全部三态缓冲** ✗）⇒ **完整 PnR 成功、出 `.fs`（7093.9 KB）** ✓✓
   ⇒ **根因 = 16 路三态（IOBUF）电极** ✗✗。

**为什么"电脑上一直能跑"** ✗✗：**增量构建复用历史布点/布线** ✗ —— 只要 `impl\` 在，
工具就不会重新布这三态网络 ✓；一旦清掉 ⇔ 换台机器/git clone/清理目录 ⇒ **立刻布不通** ✗✗。
与 §2b 属同一类："我这台电脑上能编过" ≠ "这个工程能被重新构建" ✓。

**当前状态与代价** ✗：`pad` 现在是**纯输入** ⇒ **码流能出 ✓ 但硬件上电极无法充电 ⇒ 触摸在板上不可用** ✗
（仿真仍可用：测试台自己驱动电极 ✓）。**所有非 pads 功能在板上可用** ✓
（UART 事件 ✓ 定序器 ✓ 塑谱 ✓ 效果器 ✓ 复音 ✓）。

**建议的正式修法（需用户/ZCode 定）**：✅ **已不需要！见下方 §2d（本轮已彻底解决 ✓✓）**

## 2d. ✅✅ **C0 彻底解决：三态的使能必须写成寄存器**（第 6 轮，无需任何硬件改动）

**真正的根因** ✗✗：不是"三态本身布不通" ✗，而是**三态的使能用组合逻辑推断** ✗。
Gowin 的 IOBUF 带**内置输出使能寄存器** ✓；组合推断的三态会让布线器无解 ✓。

**修法（`pad_scan.v` 三行）** ✓：
```verilog
reg pad_drv_en;
always @(posedge clk or negedge rst_n)
    if (!rst_n) pad_drv_en <= 1'b0;
    else        pad_drv_en <= (st == S_CHG);
assign pad = pad_drv_en ? {NCH{1'b1}} : {NCH{1'bz}};   // ← 三态照旧，只是使能打了一拍
```

**排除链（每一步都实测过 ✓，`-PlaceOpt 2 -RouteOpt 2` 才看得到真实条数）**：

| 配置 | 结果 |
|---|---|
| 组合三态（原始） | ❌ `86 unrouted nets` ✗ |
| 组合三态 + `OPEN_DRAIN=ON` | ❌ `86 unrouted nets` ✗（上一轮那次试验因脚本正则失效其实没生效，本轮真测 ✓） |
| 组合三态 + ④ 瘦身后的寄存器表 | ❌ `86 unrouted nets` ✗ |
| **寄存器使能的三态（当前）** | ✅ **`编译成功` + `tdm_synth.fs` 7093.9 KB + slack +15.356 ns**（历史最好）✓✓ |

**验证**：闸口 11/11 ✓、全量 28/28 ✓、`RESULT pad=PASS ps1=1 ps2=1 ps4=1 ps3=1` ✓、
`RESULT ps4inc=PASS pads=8 cross=1` ✓、`RESULT ps5=PASS diff=0 boost=239` ✓
⇒ **RC 触摸设计完整保留** ✓✓、**不需要 MPR121** ✓（原建议撤回 ✓）。

**留档工具** ✓：`tools/scripts/pad_mode.py --inout | --input | --show`
—— 一键在三态（寄存器使能版 ✓）与纯输入之间切换，**防止将来有人把它改回组合版** ✓
（往返切换已验证不累积碎片 ✓）。

**仍然需要在上板时做的事**：§1 的 RC 绝对量程不确定性 ✗ 依然存在（内部下拉电阻与电极电容未知 ✓）
⇒ 仍建议每根电极外接 **1 MΩ + 22 pF** 把 RC 定到量程中段 ✓，并按 §7 的顺序 bring-up ✓。

## 3. UART 事件在长刷新期间可能被丢

**现象**：note_map 非 IDLE 时**不看** `ev_valid` ✗ ⇒ 这期间到达的 `0x61` 事件被丢 ✗。
刷新（尤其全刷 32 声部）会占用 note_map 数百拍 ✗。
**为什么仿真测不出** ✗：我的测试台事件间隔都很大 ✓（毫秒级 ✓），从不撞上 ✗。
**上板会怎样**：快速连奏 / 上位机连发时**偶发丢音** ✗。
**缓解**：
- **pad 路径不受影响** ✓✓（`pad_scan` 会等 `!note_busy` 才发 ✓，天然握手 ✓）；
- 上位机（UART）路径：发完 `0x61` 后用 **A3 的读回**（写 `[0x0F][src]` ✓）确认，或加重试 ✗；
- 彻底修法：给 note_map 加一个小事件 FIFO ✗（下个版本，非本批必需 ✓）。

## 4. `initial` 块与存储器上电值（低风险，已双保险）

- `spec_ram`（16×8）用 `initial` 清零 ✗ —— `initial` 在综合里**不可移植** ✗；
  但 **Gowin 的 RAM 上电本来就是 0** ✓（与 `fx_delay` 线缓冲同一结论 ✓）；
- **更硬的保险**：引导 FSM 现在**显式写** `0x5A=0x02 / 0x5B=0 / 0x60=0` ✓✓
  ⇒ 即使 RAM 上电非 0，谱也是 0 ✓（这正是闸口 E3 抓到"13/16"后补的 ✓）；
- 证据：PnR 成功且 Logic 从 13661 → **15471** 上升 ✓ ⇒ `spec_ram` 被真的综合进去了，
  **不是被当黑盒丢掉** ✓（黑盒会导致资源数字不变，本项目踩过这个坑 ✗）。

## 7. 上板 bring-up 建议顺序（把风险按"先量再听"排）

0. **★ 先量触摸量程（现在有一条命令了 ✓）**：
   ```powershell
   python tools/scripts/dsp_host.py --port COM5 padmon
   ```
   —— 逐通道打印 `base / raw / raw÷base / 判定` ✓，并按 §1 判据自动判定
   "✓ 量程可用 / ✗ 封顶（RC 太慢）/ ✗ 太快（分辨率不足）" ✓✓
   **必须先过这一关**：不满足就先去调外接 R/C（建议每根 **1 MΩ + 22 pF** ⇒ RC ≈ 594 拍 ✓，
   落在 12 位计数器的中段 ✓；手指再加 ~10 pF ⇒ +270 拍 ✓ 增量 ~45% ✓✓）。
   判据：松手时 `raw ∈ [20, 2000]` ✓；按住时 `raw ≥ 1.3 × base` ✓。
   （实现见 `未验证与挂账清单.md` 的 **⑤ 电极遥测寄存器** 一节 ✓，判据
   `RESULT padmon=PASS raw3=96 base3=31 raw7=71` ✓）
1. **再听最简单的**：内置曲目（定序器 ✓，与 pads 无关 ✓）⇒ 确认 I2S/DAC/扬声器链路 ✓；
2. **再测事件通路**：串口发 `0x60/0x61` 弹几个音 ✓（这条在闸口 VP6 里已验过逻辑等价 ✓）；
3. **最后才试 pads 演奏 + 塑谱**（依赖第 0 步的量程 ✓）；
4. 每一步都用 A3 的读回（`[0x0F][addr]` → 回两字节 ✓）确认"写进去了没有" ✓
   （`python tools/scripts/dsp_host.py --port COM5 read 0x00,0x37,0x40,0x50` ✓）。

⚠️ **烧写前必做**：确认 `impl\pnr\*.fs` 是**本次构建**的产物 ✓，且构建命令带了
`-SspiAsGpio` ✓（54/55/56 = SSPI 专用脚 = DAC ✗）与 `-PlaceOpt 2 -RouteOpt 2` ✓
（否则日志里的"0 unrouted nets"是假的 ✗）。
