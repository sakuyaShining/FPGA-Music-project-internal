## 7. 惯犯陷阱（本项目已踩过的，按出现次数排）

1. **"先声明后使用"** ✗（4 次）：`reg`/`wire`/`localparam` 必须在引用它的 `always`/`assign` **之前**声明。改 FSM 时最容易犯。
2. **有符号/无符号** ✗（4 次）：**位选（`x[15:0]`）和拼接（`{a,b}`）在 Verilog 里是无符号** ✗ ⇒ 负值被**零扩展**成大正数。凡是有符号运算，先落到 `signed wire` 上再算。实测后果：输出 +50% 直流、49% 削顶。
3. **`x` 传播** ✗：复位后第一个样本引擎未定态 → 写进效果器线缓冲 → 反馈环反复回写 → 整条线变 x。已用"上电冲刷"解决（`FLUSH_LEN`）。
4. **位宽上下文** ✗：`a * b` 的宽度由上下文决定；`g*P` 在窄上下文里会溢出。显式加宽。
5. **PowerShell 处理中文** ✗：中文引号会打断 `-Command` 解析；`.ps1` 必须 **ASCII-only**（PS 5.1 把无 BOM 的 UTF-8 当 ANSI 读）。**改文本文件一律用 edit/write 工具，不要用 PowerShell 字符串替换**。
6. **陈旧构建** ✗：改完 `.v` 不重编就跑，看到的是旧行为。`build_sims.ps1` 有 mtime 检查；`regress_all.py` 自己重编（可信 ✓）。
7. **窄脉冲被慢节拍采样** ✗（3 次）：1 拍的 valid 只在 512 拍一次的 tick 上采 ⇒ 完全采不到。要么持续保持，要么用 always 块监视。
8. **`$readmemh` 静默失败** ✗：文件缺失/行宽不符 ⇒ 存储器全 x，但编译不报错。改运行目录时务必确认 hex 都在。
9. **默认值放不进位宽** ✗：`DELAY_LEN` 默认 2048 而线缓冲 2^11 ⇒ 截断成 0 ⇒ 抽头读到刚写入的样本（已改 1500，见 A5）。
10. **测试台自己的竞态** ✗：触发发生在 UART **数据字节末尾**，而 `wr_reg` 要等 234 拍停止位才返回 ⇒ "等 load_en"会假超时。用**事件监视器**而不是固定窗口。
10b. **PowerShell 文本 I/O 会加 UTF-8 BOM** ✗✗（2026-10-02 又中一次）：`Set-Content -Encoding UTF8` 写出的 `.v` 带 BOM ⇒ **iverilog 直接报 "Unable to find the root module"** ✗。**结论：改任何文本文件只用 `edit`/`write` 工具或 Python**（`open(...,encoding='utf-8-sig').read()` → 写回 `encoding='utf-8'` 可去 BOM ✓）。
10c. **反过来：`edit` 工具会去掉 `.ps1` 的 BOM** ✗✗（2026-10-03 中招）：PS 5.1 把**无 BOM 的 UTF-8 当 ANSI** 读 ⇒ 脚本里的中文注释变乱码 ⇒ **解析失败 "UnexpectedToken"** ✗。含中文的 `.ps1` 必须**带 BOM**：用 Python 写回 `encoding='utf-8-sig'` ✓。
10d. **加宽计数器后忘了改 `case` 标签** ✗✗（2026-10-03 中招，很隐蔽）：`b_idx` 从 5 位加宽到 6 位，而 case 里仍写 `5'd32`…`5'd44` ⇒ **常量回绕**成 0…12 ✗ ⇒ 引导序列从第 32 条起**写错寄存器** ✗（症状：谱 RAM 前 4 个泛音是 0、第 5 起是 **x** ✗）。**规则：改位宽后 grep 一遍所有带位宽的常量** ✓。
10e. **"能编过" ≠ "能重新构建"** ✗✗（C0 的教训）：Gowin 的**增量流程复用历史布点/布线** ⇒ 只要 `impl\` 在就"一直能编" ✓；**清一次 `impl\` 或换台机器就编不出来** ✗✗。**判据：把 `impl\` 删掉再编一次，能出 `.fs` 才算真的可构建** ✓。
   另外：**构建必须带 `-SspiAsGpio`** ✓（54/55/56 是 SSPI 专用脚 = 本工程 DAC ✗）；**`-PlaceOpt 2 -RouteOpt 2` 才能在日志里看到真实的未布线条数** ✓（默认选项报 "0 unrouted nets" 是工具没真跑 ✗）。
10f. **★★ 三态的使能必须写成寄存器** ✗✗（2026-10-03 花了整整两轮才定位）：本工程 16 路电极是 `inout`（充/放/读同一根线 ✓）。用**组合逻辑**推断三态
   （`assign pad = (st == S_CHG) ? 1 : 'bz;`）⇒ Gowin 报 `PR0004 ... 86 unrouted nets` ⇒ **出不了码流** ✗✗。
   **改成寄存器使能**（`reg pad_drv_en; always @(posedge clk…) pad_drv_en <= (st == S_CHG); assign pad = pad_drv_en ? 1 : 'bz;`）
   ⇒ **编译成功** ✓✓（`.fs` 7093.9 KB、slack +15.356 ns ✓）。
   已排除：`OPEN_DRAIN=ON` ✗、寄存器表瘦身 ✗、`DRIVE=8` ✗、`PULL_MODE` ✗、`initial` 块 ✗。
   **工具**：`python tools/scripts/pad_mode.py --inout|--input|--show` ✓ 一键切换、防回归 ✓。
10g. **★★ 本设计一直贴着"布线悬崖"** ✗✗（第 7 轮）：RW 资源不是问题（Logic 70% ✓），**布线资源**才是 ✗。
   实测：在已经能出码流的版本上**只加一个电极遥测功能** ⇒ 未布线从 0 涨到 **187 条** ✗✗。两条便宜原则：
   ① **绝不要随便读 `R[addr]`（`regs_flat`）** ✗ —— 它的**每一个切片都会综合出一棵 NW:1 读 mux** ✗，
      全设计几十个切片；新功能需要寄存器时，**用专用寄存器走普通写通路** ✓（这一条把 187 降到 54 ✓）；
   ② **`reg_bank` 的项数越少越好** ✓：从 256 缩到 **128**（0x00–0x7F 已覆盖全部冻结地址 ✓）
      ⇒ 未布线 **54→0** ✓✓，还附送 **省 677 LUT + 797 个 FF** ✓（Logic 15185→14508 ✓、Register 4366→3569 ✓）。
      注：当年"缩到 128 报 EX3784"的障碍来自那张 256 项并行版初值表 ✗ —— 它已在第 5 轮按 §3 重写 ✓，障碍消失 ✓。
10h. **★★ `fx_delay` 的 `sample_en` 必须是【÷12 频闪】** ✗✗（第 8 轮，害我查了很久）：该模块内部是
   **12 态 FSM** 且 `else if (sample_en)` ⇒ **每态只在 sample_en 那一拍推进** ✓ ⇒ **一整遍 = 12 个频闪** ✓。
   把它接成恒 1 ✗（我以为每拍一个样本 ✓）⇒ 实测**输出恒 0** ✗✗（看起来像"功能坏了" ✗）。
   **正确用法**照 `tb_fx`：`reg [3:0] pc; wire sample_en = (pc == PERIOD-1);` ✓，
   录音时**等 12 个频闪**再取一个输出 ✓（= 一整遍 ✓）。
   配套教训：测试台的 `while (cond) @(posedge clk);` **一旦条件不成立就是仿真空转** ✗ ——
   本项目仿真的超时是 **40 秒仿真时间 = 10.8 亿拍** ✗✗（会跑几小时 ✓）。调试期务必用固定拍数 ✓。
10j. **★★ 湿声路径的"域"必须对齐（D1，2026-10-03 第 9–10 轮）** ✗✗：`fx_delay` 的线缓冲是 **16 位** ✓，
   而干声 `din` 是 **24 位** ✓。原来的混音 `mix_sum = dry + wet` 里，湿声只是把抽头**符号扩展**到 24 位
   （数值不变 ✗）⇒ 满幅抽头在 24 位域里只有 1/128 = **42 dB 偏低** ✗✗
   ⇒ **混响/延迟/合唱全都几乎听不见** ✓，而 demo 里"听得见的混响"其实是 `RV_FB=0.75` 时
   线缓冲**饱和削顶**产生的自激失真 ✗✗（假象 ✓）。
   **修法**：湿声先 `wet_sum <<< 8` 再按 `wet_sh` 衰减 ✓（满幅 32767<<8 = 8388352 恰好不越 24 位 ✓）。
   **联动**：所有"以线缓冲域为绝对幅度预期"的判据都要同步 ✗ —— 例如 `fx_check.py` 的
   `--imp` 默认从 5000 → **1280000**（= ×256 ✓，已注明原因 ✓）。
   **顺带**：`RV_FB` 默认也因此从 `0xC0`(0.75, 91.9% 削顶 ✗) 降到 **`0x80`** ✓。
10k. **★ 闸口工具会被"文件锁"弄崩** ✗（第 9 轮）：本机常驻有工作区监视进程（实测 **ZCode 有 16 个进程**在跑 ✗），
