## 二、你的码流我逐行看了，有四处要改

前三条是真 bug（都能一行改掉），第四条现在不发作但进产品前必须补。

### 缺陷 1（致命）：`cfg_ok` 校验的是"自洽"，不是"和写进去的比"

```verilog
cfg_ok <= (calc_crc == {rx_mem[BYTES+1], rx_mem[BYTES]});
```

左边是**读回数据**算的 CRC，右边是**从 EEPROM 里读出来的** CRC 两字节 ——
而这个 CRC 是**写的时候一起写进同一片 EEPROM 的**。

所以这个判据问的是"EEPROM 里存的数据和它自己存的 CRC 对不对得上"，
不是"EEPROM 里的数据是不是我刚写的那一份"。

顶层 `cfg_out` 声明了，**从头到尾一次都没用过** —— 少的就是那一句：

```verilog
cfg_ok <= (calc_crc == {rx_mem[BYTES+1], rx_mem[BYTES]}) && (cfg_out == cfg_in);
```

**后果**：
- 空白芯片上这个测试是**有效的**（全 `0xFF` 的 CRC 是 `0xE313` ≠ `0xFFFF`，第一轮必然失败）——
  你 `00-说明.md` 里这点说对了。
- **但从第二次上电开始就失效了。** EEPROM 非易失，上次跑完 `0x0000`/`0x0040` 各躺着一对
  合法的 (数据, CRC)。这次上电第一轮读 → CRC 自洽 → **`led[5]` 立刻亮**，哪怕这次一次都没写成。

它能抓"写从来没成功过"，抓不到"写曾经成功、现在坏了"——而后者正是上板最需要抓的。

### 缺陷 2（潜伏）：读的最后一个字节回了 ACK，不是 NACK

```verilog
RXACK: case (ph)
    2'd0: begin sda_lo <= 1'b1; ph <= 2'd1; end   // 无条件 ACK
```

I²C 规矩：主机读 N 字节，前 N-1 个回 ACK（继续要），**第 N 个必须回 NACK**（到此为止）。
你 58 个读字节**全部**回了 ACK。

**为什么平时看不出来**：24LC256 收到 ACK 会继续把**下一格**推到 SDA 上。你写完
`0x0000..0x0039`，ACK 之后从机要送的是 **`0x003A`** —— 你没写过它，空片上是 `0xFF`，
bit7=1，从机放开 SDA，**STOP 恰好还能成立**。

**什么时候会炸**：那一格只要是 `0x00`（或任何 bit7=0 的值），从机就把 SDA 按住，
STOP 的上升沿不存在，**总线当场卡死**，接着进 `RECOVER`，再叠上缺陷 3 → 静默丢请求。

**修法（一行）**：

```verilog
2'd0: begin sda_lo <= (rx_idx == rx_len - 8'd1) ? 1'b0 : 1'b1; ph <= 2'd1; end
```

**这条我仿真验证过了**，不是纸上推的：自写 24LC256 行为模型 + 7 项判据，

- 你的原版：7 项红 4 项（`ACK=58`、`NACK=0`、末字节=ACK、`0x003A=0x00` 时 STOP 从 2 掉到 1）
- 换成上面那一行：**7 项全绿**

### 缺陷 3（独立）：`RECOVER` 放弃请求，但没告诉上层

```verilog
if (st == FINISH && mode == 2'd2) begin save_pend <= 1'b0; load_pend <= 1'b0; end
```

注释写明了是**故意**不自动重试（怕无限循环）——这个取舍合理。
问题是**没把"这次请求被放弃了"报出去**：`err` 只在"恢复后 SDA 仍为低"时才置位，
恢复成功就 `err = 0`，上层看到的是"这次什么都没发生"。

而 `eeprom_exercise_top` 是**按定时器推进**的（`tick` 一到就换状态），
不检查上一次请求有没有真的执行 ⇒ 一次被丢的 `save` 完全无声。

**这一条和缺陷 1 组合起来才是真危险**：

> `save` 被静默丢弃 ⇒ EEPROM 里留着上一轮的旧数据 + 旧 CRC ⇒ 仍然自洽 ⇒ `led[5]` 照样亮。

**"请求被丢" + "判据只查自洽" = 绿灯掩盖故障。**

修法：`FINISH` 里 `mode == 2'd2` 时无条件 `err <= 1'b1`（恢复成功也报，让上层知道这次没做），
或者加一个 `dropped` 脉冲给上层。

### 缺陷 4（结构性，现在不发作）：没有时钟拉伸容忍，也没有"等总线空闲"

这两条在 `engine/src/i2c_master.v` 里本来是有的，重写时没带过来：

| 能力 | `i2c_master.v` | 你这份 |
|---|---|---|
| 末字节回 NACK | 有 | **没有**（缺陷 2） |
| 时钟拉伸容忍 | `wire stretch = (~scl_lo) & (~scl_sync);` | **没有** —— 模块连 `scl_in` 输入都没有 |
| 发 START 前等总线空闲 | `start_wait = st==S_START && ... && (!sda_sync \|\| !scl_sync)` | **没有** |

`cfg_eeprom_store` 是**纯开环**的：SCL 是推挽输出，从不回采。所以它按自己的节奏翻 SCL，
总线上的实际情况一概不知。

**为什么现在不发作**：FPGA 独占总线，24LC256 正常读写时不拉伸 SCL。所以上板大概率跑得通。

**什么时候会坏**：
- 载板那条 I²C 中间有 `TCA9517DGKR`，缓冲器两侧的时序不是你说了算的；
- 总线上只要再多一个设备（比如 MCU 也来读），或者从机忙时拉伸，你就直接采到错数据，
  而且**不会报错** —— 和缺陷 1 一样是"静默错"。
- 上电瞬间如果从机还没释放 SDA，你没有 `start_wait`，第一个 START 会直接撞车。

这一条**不急**，但如果这套东西将来要进产品（不只是测试），必须补。补的时候建议**直接升级
`i2c_master.v` 成流式引擎**（它已经有 NACK、拉伸、空闲等待三样），比在这份上补三样更省事。

## 三、还有一处单位算错（跟上面三条无关，但会误导人）

```verilog
localparam integer WR_WAIT = CLK_HZ / 100;   // 注释写 10 ms
...
WAIT: begin wcnt <= wcnt + 1; if (wcnt >= WR_WAIT) st <= FINISH; end
```

`WAIT` 只在 `q` 拍（`tick` 满 `DIV` 个时钟）时执行一次，所以 `WR_WAIT` 的单位是 **q 拍**，
不是时钟拍。27 MHz / 100 kHz 下 `DIV = 68`：

> 实际等待 = `10 ms × 68` = **680 ms**，一轮 save + load ≈ **1.37 s**。

readme 里写"每轮约 1.5 秒"，看的人不会觉得不对——**那是巧合撞上的，不是设计**。

修法：`localparam integer WR_WAIT = (CLK_HZ / 100) / DIV;`（取整后 270000/68 ≈ 3970 拍 ≈ 10 ms）。
