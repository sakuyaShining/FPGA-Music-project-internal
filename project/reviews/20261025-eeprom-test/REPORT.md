# eeprom-test.zip 核对与判定 · 2026-10-25

**收到**：`eeprom-test.zip`（152,150 B，SHA256 `3f98a29de402a93c…`，全文见 `evidence/eeprom-test-receipt.json`）
**来源**：队友（写 `cfg_eeprom_store.v` 的一方）
**背景**：队友要一段**真实**的 I²C 波形（一次写 + 一次读），外加**芯片型号**与**上拉电阻**两个数字。
这个包是他给的替代方案：**"不用示波器，看 LED 就行"**。

**一句话结论**：包是真的、码流是给这块板子的，但它**证明不了它声称要证明的那件事**——
`led[5]` 亮只说明"EEPROM 里躺着一对自洽的数据+CRC"，不说明"我们写进去的字节回来了"。
另外读事务的**最后一个字节回了 ACK 而不是 NACK**，是颗潜伏的雷（这次恰好绕开了触发条件）。
两处叠加后，存在"写已经死了、灯还是亮的"这条路径。

## 三、这个测试证明不了它想证明的事（判据 / 协议 / 恢复三处）

`eeprom_exercise_top.v` 的主循环是：
`读 → 等 → 图案+1 → 写 → 等 → 读 → …`，`led[5]` 由 `cfg_ok` 置位、`led[3]` 由 `err` 置位，
两个都是**只置位不清零**（所以准确说是"历史上曾经通过/曾经错过"，不是"最近一次"）。
LED 极性、引脚（`led[5]`=20、`led[3]`=18）都对得上产品约束与共阳极接法，这部分没错。

问题在两处判据。

### 3.1 缺陷一：CRC 校验的是"自洽"，不是"和写进去的比"

`cfg_eeprom_store.v:314`：

```verilog
cfg_ok <= (calc_crc == {rx_mem[BYTES+1], rx_mem[BYTES]});
```

- `calc_crc` = 对**读回的数据**算的 CRC16-CCITT
- `rx_mem[BYTES]` / `[BYTES+1]` = **从 EEPROM 里读出来的** CRC 两字节

而这个 CRC 是**写的时候一起写进同一片 EEPROM 的**（`tx_mem[3+BYTES]`、`tx_mem[3+BYTES+1]`）。
于是这个判据等于在问"**EEPROM 里存的数据和它自己存的 CRC 对不对得上**"，
而不是"**EEPROM 里的数据是不是我刚写的那一份**"。

顶层把 `cfg_out` 声明出来了，**从头到尾一次都没用过**：

```verilog
wire [8*BYTES-1:0] cfg_out;   // 声明
// ……再没有出现
```

少的就是那一句 `cfg_out == cfg_in`。

**后果分两层：**

1. **在空白芯片上，这个测试是有效的。** 全 `0xFF` 的 56 字节算出来 CRC = `0xE313` ≠ `0xFFFF`，
   第一轮读必然失败（`00-说明.md` 这点说对了），只有写成功之后才会亮。
2. **从第二次上电开始，这个测试失效。** EEPROM 是非易失的：上次跑完，`0x0000` 和 `0x0040`
   两个副本里各躺着一对合法的 (数据, CRC)。这次上电第一轮读 `0x0000` → CRC 自洽 → **`led[5]` 立刻亮**，
   哪怕这次写一次都没成功。

也就是说：**它能抓"写从来没成功过"，抓不到"写曾经成功、现在坏了"。**
而后者恰恰是上板调试最需要抓的那一类。

### 3.2 缺陷二：读的最后一个字节回了 ACK，不是 NACK（这次侥幸没咬到）

`cfg_eeprom_store.v:273-287`：

```verilog
RXACK: begin
    case (ph)
    2'd0: begin sda_lo <= 1'b1; ph <= 2'd1; end   // 无条件拉低 SDA = ACK
    ...
    default: begin ... rx_idx <= rx_idx + 8'd1;
                 if (rx_idx + 1 >= rx_len) st <= STOP;   // 最后一个字节也 ACK 了，然后 STOP
```

I²C 主机的规矩是：**读最后一个字节要回 NACK**（释放 SDA），让从机交出总线，再发 STOP。

24LC256 收到 ACK 会**继续把下一字节送到 SDA 上**。于是 STOP 能不能成立，取决于
"最后一个字节之后那个字节"的 bit7：

- bit7 = 1 → 从机也释放 SDA → 主机释放时 SDA 正常上升 → **STOP 成立，看不出问题**
- bit7 = 0 → 从机把 SDA 按住 → 主机 `sda_lo <= 1'b0` 释放后 SDA **不上升** → **STOP 不成立**

**这次是后者没发生。** 算一下地址就明白：

| 事务 | 覆盖的 EEPROM 地址 |
|---|---|
| 写（`tx_len = 56+5 = 61`，前 3 字节是设备+地址） | `0x0000..0x0039`（58 字节） |
| 读（`rx_len = 56+2 = 58`） | `0x0000..0x0039` |
| **ACK 之后从机要送的那一个字节** | **`0x003A`** |

`0x003A` **从来没被写过**，空白芯片上就是 `0xFF`，bit7 = 1 ⇒ 从机释放 SDA ⇒ STOP 正常。
**所以这一条在这个测试里不会发作**，`led[5]` 不会被它污染。

但它是颗雷，不是无关紧要：

- 若哪天把 `BYTES` 改大（比如 62，`PAGE_OK` 还允许），最后一个读地址就顶到 `0x003D`，
  ACK 之后那一个字节变成 `0x003E` —— 仍是 `0xFF`，还是躲过去；
  但**只要有一次写满 64 字节页**（产品里非常常见），`0x003A` 就会被真实数据占掉，
  那一刻开始 STOP 失败是**数据依赖的间歇故障**。
- 若换用 `i2c_master.v` 那条链路、或把配置区从 `0x0000` 挪开，结论就变了。

**结论：这一条不该按"这次没问题"放过，但也不该按"这次就会挂"上报。** 它的准确定性是
**潜伏的协议违规**，本测试恰好绕开了触发条件。修法仍然是一行（§6.2）。

### 3.3 `RECOVER` 会静默吞掉请求（这条是独立的真问题）

`IDLE` 里有个总线恢复分支：进入条件 `sda_q == 1'b0`（从机拉着 SDA）。走完 `RECOVER` 后，
`FINISH` 把 `save_pend/load_pend` **清掉**（`cfg_eeprom_store.v:126`）：

```verilog
if (st == FINISH && mode == 2'd2) begin save_pend <= 1'b0; load_pend <= 1'b0; end
```

注释写得很清楚是**故意**的（"不能在这里自动重试——那会形成无限循环"），这个取舍本身合理。
问题是**没有把"这次请求被放弃了"告诉上层**：`err` 只在"恢复后 SDA 仍为低"时才置位，
若恢复成功（SDA 已放开）则 `err = 0`，上层看到的是"这次什么都没发生"。

`eeprom_exercise_top` 的状态机是**按定时器推进**的（`tick` 一到就换状态），
不检查上一次请求有没有真的执行 ⇒ **一次被丢弃的 `save` 会完全无声**。

这一条和 §3.1 组合起来才是真正的危险：

> `save` 被静默丢弃 ⇒ EEPROM 里保留上一轮的旧数据 + 旧 CRC ⇒ 仍然自洽 ⇒ `led[5]` 照样亮。

**"请求被丢" + "判据只查自洽" = 绿灯掩盖故障。** 而 §3.2 恰好是唯一可能触发 `RECOVER` 的路径，
所以这两条不是无关的两件事，是一条链。

### 3.4 那到底为什么还需要真实波形

把上面三条摆清楚之后，波形的价值不在于"能看出哪个 bug"，而在于**它是唯一能证伪这套判据的东西**：

- §3.1 是**判据覆盖**问题，波形看不出来，必须改代码（加 `cfg_out == cfg_in`）。
- §3.2 是**协议**问题，波形一看就明白（数一下第 9 个时钟之后 SDA 是谁拉的），
  但它在这次的数据下不发作 —— 所以"看 LED"永远发现不了它。
- 而队友说"三次都卡在自写的假芯片上"，恰恰说明**他的假模型和真芯片之间还有没对齐的地方**。
  真实波形是唯一能把"我以为的总线"和"真实的总线"逐拍对齐的东西。

**所以：他要波形的直觉是对的；"看 LED 就行"是把一个能定位问题的手段换成了一个只能给结论的手段。**
更麻烦的是这个结论（§3.1）本身还不成立。

## 四、他要的两个数字，我们现在能答了

这两个数字他问我们，我们其实**仓库里就有**——他自己没查（或者他的树里没有 `hardware/`）。

### 4.1 芯片型号：`24LC256-I/SN`

来源：`hardware/current/native/sch/Schematic1/02_Shift_and_memory.esch2`（原理图第 2 页
"Shift and memory"）与 `hardware/current/native/pcb/PCB1.epcb2` 的 BOM 字段：

| 项 | 值 |
|---|---|
| Manufacturer Part | **`24LC256-I/SN`**（Microchip 美国微芯） |
| LCSC Part Name | 256K I²C 串行 EEPROM |
| Supplier Part | `C411625` |
| Footprint | SOIC-8（`SOIC-8_L5.0-W4.0-P1.27-LS6.0-BL`） |
| Memory Size | 256 Kbit（32 KB） |
| Interface | I²C，400 kHz |
| Write Cycle Time (Tw) | 5 ms |
| Endurance / Retention | 100 万次 / 200 年 |
| Voltage | 2.5–5.5 V |

**对 RTL 的含义**：2 字节地址、**64 字节页**、写周期 5 ms、7 位地址 `0x50`（A0/A1/A2 全接地）。
他代码里 `BYTES=56` ⇒ 一次写事务 = 3 + 56 + 2 = **61 字节 ≤ 64**，不跨页，`PAGE_OK` 断言站得住。
`WR_WAIT = CLK_HZ/100 = 10 ms` 也够（规格 5 ms）。

> 也就是说：**`00-说明.md` 里的"24C256"不是猜的，是对的。** 但这是他代码的输入假设，
> 却是他同时问我们要的两个数字之一 —— 说明他自己并不确定。现在确定了。

### 4.2 上拉电阻：`4.7 kΩ`（载板上共 4 颗）

| 位置 | 位号 | 阻值 | 说明 |
|---|---|---|---|
| 第 13 页 `13_Power_off_isolation` | **R60 / R61** | **4.7 kΩ** 0603 ±1%（`0603WAF4701T5E`） | 配 `U14 = TCA9517DGKR`（I²C 电平转换/隔离） |
| 第 3 页 `03_Display_harnesses` | **R33 / R34** | **4.7 kΩ** 0603 ±1% | 模块侧 |

载板把 I²C 用 `TCA9517DGKR` 切成两段：
`I2C_SDA`/`I2C_SCL`（3V3_IO，FPGA 侧）↔ `I2C_MOD_SDA`/`I2C_MOD_SCL`（3V3_PERIPH，模块侧）。
全 14 张原理图里 4.7 kΩ 一共 5 颗，其中 **4 颗在 I²C 上**（两条线 × 两段）：
R33/R34 + R60/R61。第 5 颗是 `06_Controls` 的 **R52**，那一页只有
`ENC_A/ENC_B/ENC_PUSH/EDIT/PRESET0..3`，**与 I²C 无关**。
本仓库 `constraints/tdm_ship_board.cst` 的注释也写着
"开漏：需要外部上拉。载板上有 4.7k 到 3V3" —— 与原理图一致。

> 证据边界：位号、阻值、所在页、以及 TCA9517 把总线切成两段，这些是**从原理图文件里直接读出来的**。
> "哪一对在哪一段"是按页功能推断的（第 13 页是隔离页、第 3 页是模块侧线束页），
> **没有逐根导线核对**。要钉死这一点得看 PCB 走线或直接量。

**但要注意场景差别**：

- **在载板上**：上拉是板载的，不用外加。
- **裸 Nano 20K + 外接 EEPROM 模块**：板子上没有 EEPROM、也没有上拉，
  **必须外接 4.7 kΩ**，或者用带板载上拉的 EEPROM 模块。
  `tdm_ship_board.cst` 里还给了 `PULL_MODE=UP` 的内部弱上拉兜底，但那不是给 100 kHz 用的。

### 4.3 引脚：25 / 26，且**与 LCD 的 HS/VS 共用**

`hardware/current/context/pin-map-audit-20261024.md` 逐脚核对过：

```
STORE_SDA,25,J6,10  →  J6-10  →  25  ✅
STORE_SCL,26,J6,11  →  J6-11  →  26  ✅
```

同一份文档第 133-134 行又写着 `10 | 25 | LCD_HS | FPC 座`、`11 | 26 | LCD_VS | FPC 座`。
它把这些脚归在"**FPC 座相关（不插屏可用）**"一类里（第 290 行）。

**⇒ 插着屏的时候，25/26 被屏的 HS/VS 占用，不能同时当 I²C 用。**
接线前必须先确认屏没插（或屏的这两根没接）。

## 五、文档与实现的小偏差（不影响结论，但会误导人）

| # | 文档说法 | 实现 | 影响 |
|---|---|---|---|
| 1 | "约每 1.5 秒一轮" | `WAIT_BITS=22` ⇒ 4 × 2²² / 27e6 = **621 ms** | 判读时机对不上（差 2.4 倍） |
| 2 | "载板上只有 20 和 18 两个脚是 LED（其余被扫描链占用）" | 引脚审计已定：**载板不征用任何 LED 脚**，`15..20` 六个都在 | 旧顾虑的残留，无害（另外 4 个被驱动为灭） |
| 3 | "SCL_HZ = 100_000" | `DIV = (27e6+2e5)/4e5 = 68` ⇒ 实际 **99.27 kHz** | 算时序余量时别按整 100 k 算 |
| 4 | "逻辑分析仪随便抓一段就能同时看到读和写" | 与"不需要示波器"自相矛盾 | 只是措辞 |

一处**没错但值得记**的：顶层两个锁存位都是**只置位、不清零**的
（`if (err) err_q <= 1'b1;`、`if (cfg_ok) ok_q <= 1'b1;`，都没有清路径）。
所以：

- 第一轮哪怕因为上电时序擦出一次 NACK，`led[3]` 会**一直亮到断电**，后面恢复正常也不灭
  ⇒ 判读时要知道"`led[3]` 亮"只代表"**曾经**错过一次"
- `led[5]` 一旦亮起，**即使之后写全坏掉也不会灭**
  ⇒ "灯亮着"只能证明"历史上成功过一次"，这跟 §3.1 是同一个病根

## 六、判定与建议

### 6.1 分项判定

| 问题 | 答案 |
|---|---|
| 包是真的吗？有没有被篡改？ | **真的**，6/6 校验和一致 |
| 码流是给这块板子的吗？ | **是**，`GW2AR-LV18QN88C8/I7` / QFN88 / 同版本工具 |
| 能烧吗？ | **能**，与 `board.fs` 同一套流程（含 `0x00006020` 的预期报错） |

### 6.2 建议的三步（按性价比排序）

- 不亮 ⇒ 先查硬件，别急着怀疑 RTL

```verilog
// 缺陷一（§3.1）：加一句相等比较，让判据从"自洽"变成"和写进去的一致"
if (cfg_ok && (cfg_out == cfg_in)) ok_q <= 1'b1;

// 缺陷二（§3.2）：最后一个字节回 NACK（RXACK 的 ph0 加条件）

// 缺陷三（§3.3）：恢复流程丢弃请求时要让上层知道，别静默

    save_pend <= 1'b0; load_pend <= 1'b0;

end
```

> 第三条有个副作用要他自己权衡：`err` 一旦置位，顶层 `err_q` 就锁死到断电
> （§5 那条）。真改的话建议同时给 `err_q` 加清零路径，否则灯会一直红着。

## 八、仿真取证：把 §3.2 从"从代码推"变成"跑出来的"

§三的三条判据是读 RTL 推出来的。读代码会看错——§3.2 我自己就错过一次。
这一节把能靠仿真钉死的部分钉死，并明确标出哪一段仍然只是推断。

### 8.1 做了什么

| 件 | 位置 | 作用 |
|---|---|---|
| 24LC256 行为模型 | `fpga/current/eeprom_probe/tb/ee24lc256.v` | 自写。关键行为：主机 ACK 之后，从机**立刻**把下一字节 bit7 推上 SDA |
| 判据测试台 | `.../tb/tb_ack_last.v` | 7 项判据，专查读事务结尾 |
| 差分驱动 | `fpga/current/tools/run_probe_sim.py` | 基线必须红在 4 条、变异必须全绿，两个一起才叫通过 |
| 捕获解码器 | `fpga/current/tools/eeprom_capture_decode.py` | 把 `TTTTTT,S,D` 边沿流还原成事务 |
| 板上探针 | `fpga/current/eeprom_probe/eeprom_capture_top.v` | 边沿捕获 + UART 回放，用于真芯片（见 §8.5） |

被测的 `cfg_eeprom_store.v` 是**原样拷贝**，`build_probe.py` 和 `run_probe_sim.py` 都断言
它的 sha256 等于 `ce40c936c63f09e7…` —— 它一变，跑出来的就不是他的代码。

### 8.2 结果：缺陷确实存在，且位置就在 `RXACK`

`python tools/run_probe_sim.py` 跑两遍同一个测试台，只换 `cfg_eeprom_store.v`：

| 判据 | 基线（他的代码） | 变异（末字节改回 NACK） |
|---|---|---|
| 读字节数 = 58 | 58 ✅ | 58 ✅ |
| 主机 ACK 次数 = 57 | **58 ❌** | 57 ✅ |
| 主机 NACK 次数 = 1 | **0 ❌** | 1 ✅ |
| 末字节是 NACK | **0 ❌** | 1 ✅ |
| A 段 STOP = 2（空片） | 2 ✅ | 2 ✅ |
| B 段 STOP = 2（`0x003A=0x00`） | **1 ❌** | 2 ✅ |
| `cfg_ok` = 1 | 1 ✅ | 1 ✅ |

- **基线 7 项红 4 项**，红的正是 §3.2 预言的那四处。
- **变异 7 项全绿** —— 说明这 4 条判据确实在测这件事，不是"怎么改都红"。
- A 段 STOP 仍然成立（2 ✅）—— 印证 §3.2 的"这次侥幸没咬到"：
  `0x003A` 在空片上是 `0xFF`，bit7=1，从机 ACK 之后放开了 SDA。
- B 段把 `0x003A` 预写成 `0x00`，**STOP 从 2 掉到 1** —— 雷当场炸了。

变异的那句改动只有一行：

```verilog
// 原来（无条件 ACK）
2'd0: begin sda_lo <= 1'b1; ph <= 2'd1; end
// 改成
2'd0: begin sda_lo <= (rx_idx == rx_len - 8'd1) ? 1'b0 : 1'b1; ph <= 2'd1; end
```

**所以修法是明确的、一行的、可验证的。**

### 8.3 解码器把捕获还原成事务（这才是能交给队友的东西）

仿真导出的捕获（格式与板上探针的 UART 文本逐字节相同）解出来是这样：

```
事务 1: 1 段, 有 STOP
  S  @0  写 0xA0  帧数 61
       写 60 帧（含 2 字节地址指针），从机 ACK 60/60
       指针 0x0000  数据 58 字节
事务 2: 2 段, 有 STOP            ← A 段（0x003A=0xFF）
  S  @0  写 0xA0  帧数 3
  Sr @0  读 0xA1  帧数 59
       读 58 字节：ACK×58  NACK×0  末字节=ACK
       末 3 字节: 0x00->ACK  0xAF->ACK  0x99->ACK
```

B 段同一份捕获，只有最后一行不同：

```
事务 2: 2 段, **没有 STOP —— 总线被从机按住**
```

顺带钉死了一件事：写进去的 CRC 两字节是 `0xAF 0x99`（即 `0x99AF`），
和 §3.1 算出来的 56 个 `0x00` 的 CRC 一致；读回来也确实是这两个字节，
所以 `cfg_ok=1`。**这正是 §3.1 说的问题**——CRC 和它保护的数据是一起写进去的，
`cfg_ok` 通过只说明"EEPROM 里的东西自洽"，不说明"等于 `cfg_in`"。

### 8.4 顺手抓到的两件事（与队友代码无关，但会咬到我们自己）

1. **`WR_WAIT = CLK_HZ / 100` 的单位是 q 拍，不是时钟拍。**
   q 拍 = `DIV` 个时钟，27 MHz 下 `DIV=68`，所以"等 10 ms"实际等了 **680 ms**，
   一轮 save+load 约 **1.37 s**。readme 里写"每轮约 1.5 s"，看的人不会觉得不对——
   那是巧合撞上的，不是设计。仿真把时钟降到 2.7 MHz（`DIV` 从 68 变成 7）才跑得动，
   实测 save 75.861 ms / load 75.820 ms，正好是 `10 ms × 7`。
   **这条独立于 ACK 缺陷，得单独修。**

2. **`%0s` 传 task 参数只认低 64 位。**
   中文标签会被切成半个字（`读字节数` → `��数`），超过 8 字符的 ASCII 标签会被截掉左边
   （`read_bytes` → `d_bytes`）。表现是"判据看起来在跑，但看不懂它在说什么"，
   和 TEST-REGISTRY §3 第 3 条是同一类事故。⇒ 标签一律 ≤ 8 字符纯 ASCII。

### 8.5 硬件：烧进去了，但没读到串口（诚实记录）

> **⚠ 本节末尾的"结论"是错的归因，正确结论见 §8.5.1。**
> 原文保留，因为"把 UART 不通误判成烧录失败"这件事本身就是一条教训：
> 手上没有独立的成功判据时，人会把自己看不懂的现象归给最近的那个可疑对象。

- 板子在：`--scan` 报 `GW2AR-18C`，ID `0x0000081B`，下载器 `Gowin USB Cable(FT2CH)`。
- `programmer_cli --operation_index 1`（`tools/scripts/flash.cmd` 用的就是这个）
  **0.18 s 就返回、没有进度条**，之后串口一个字节都没有。
  ⇒ 怀疑 `Reprogram` 对这块板子是"从板载 flash 重新配置"，**不是**下载新码流。
  换成 `--operation_index 4`（SRAM Program and Verify）才有进度条、耗时 11.5 s、
  烧到 100%，**但读回校验报 `Error found`**。
- 之后串口仍然无输出（COM5/COM6 都静默），紧接着 JTAG 扫描开始超时、
  COM 口一度全部消失（FT2232 重枚举），重枚举后 JTAG 仍扫不到。
- **结论：这两步（§6.2 第 0 步、第 2 步的上板部分）没有完成。** 需要给板子断电重插。

待查清单（板子恢复后按顺序）：

1. `--operation_index 1` 到底做了什么 —— 如果是"从 flash 重配"，那 `flash.cmd` 一直是错的，
   这条影响的不只是本次探针。
2. op 4 的 `Error found` 是真校验失败，还是读回路径本身不可用。
3. 板子形态：**载板（板载 24LC256 + 4.7k）还是裸 Nano 20K + 外接模块？**

   探针 cst 里已经把这条写成注释了。
4. 串口到底在哪一路：`COM5` 还是 `COM6`（FT2232 双通道）。

### 8.5.1 更正：烧录一直是成功的，断的是 UART 通路

板子断电重插后 JTAG 恢复（`--scan` 0.82 s，不再超时）。按顺序做了三个实验，
每个实验都只回答一个问题：

| # | 问题 | 做法 | 结果 |
|---|---|---|---|
| ① | `Status Code 0x6020` 是烧录失败吗 | `op0`：**只读设备码，不写任何东西** | 同样报 `0x6020` ⇒ **它是设备固有状态，与烧录成败无关** |
| ② | 码流到底加载了没有 | 比对 bitstream 头里的 `UserCode` 与设备读回值 | 探针 `0x0000D356` ↔ 读回 `0x0000D356`；诊断码流 `0x0000E5ED` ↔ 读回 `0x0000E5ED` ⇒ **两次都加载成功** |
| ③ | 是探针逻辑卡住了吗 | 烧一个只做两件事的码流：每 0.5 s 发 `U\r\n` + `led[0]` 闪 | **COM5/COM6 都是 0 字节** |

③ 是关键：那个诊断码流没有 I²C、没有捕获缓冲、没有任何能阻塞的状态机，
连它都发不出一个字节，就不是探针的问题。

然后查串口身份，根因在这里：

```
COM5  USB VID:PID=0403:6010 SER=2025030317A
COM6  USB VID:PID=0403:6010 SER=2025030317B
```

`0403:6010` = **FTDI FT2232H 双通道**，即 Gowin 外接下载器 `FT2CH` 本身。
整个设备列表里**没有任何板载 BL702 的设备**。

⇒ **板子的 USB-C 口没插，pin 69（`uart_tx`）是悬空的。**
PC 上那两个 COM 口是下载器的两个通道，与 FPGA 的 UART 引脚没有电气连接。
这一条解释了全部现象：烧录走 JTAG（通），UART 走板载 BL702（没插）。

**连带更正两件事：**

- `--operation_index 2`（`SRAM Program`）**是能用的**。之前只试了 1 和 4，
  漏掉了 2，于是把"烧录成功但串口没声"误读成"烧录失败"。
- `op4` 的 `Error found` 与 `op0` 的 `0x6020` 是同一个状态码，**不是真校验失败**。
- `tools/scripts/flash.cmd` 用的 `op1`（`Reprogram`）仍存疑：0.18 s 返回、无进度条。
  这一条**仍未验证**，但它影响的不是本次探针。

**仍未完成**：插上板载 USB-C 后 UART 能否收到，未验证。

### 8.6 这一节的证据边界

- **仿真证明的是 RTL 的行为，不是真芯片的行为。** `ee24lc256.v` 是我们按数据手册写的模型，
  "ACK 之后立刻推下一字节 bit7"这一条是模型里**手写进去的假设**。
  真片是不是这样，只有上板才认。所以 §8.2 的结论应当读作：
  "他的代码在**符合手册的** 24LC256 上会这样做"，而不是"在实物上已经这样做了"。
- 模型自己错过两次（`bit` 索引错位、NACK 后不放开总线），两次都是被**变异验证**抓出来的。
  这说明"模型 + 判据"这一对必须一起验，只验一个没有意义。
- §8.5 的硬件部分没有产出任何波形证据。

**最重要的一条（2026-10-25 17:45 补充）：手上只有裸 Nano 20K，没有 24LC256。**
这一条改变了"上板能拿到什么"的边界，必须写在前面而不是脚注里：

| 想要的东西 | 裸板能给吗 | 为什么 |
|---|---|---|
| SCL 时序、START/STOP 条件、地址字节 `0xA0` 的位模式 | **能**，是真的 | SCL 是推挽输出，SDA 由主机拉低 / 释放后靠内部 `PULL_MODE=UP` 拉高 |
| 主机 ACK / 数据读回 | **不能** | 没有从机，SDA 恒为高 ⇒ 写方向全 NACK，读方向全 `0xFF` |
| §3.2 的"末字节 ACK 把总线按住" | **不能显形** | 要按住 SDA 的是**从机**；没有从机，主机自己释放 SDA 后 STOP 照常成立 |

所以裸板能产出的是**主机侧的真实波形**，不是"一次完整读写的真实波形"。
队友要的是后者。要拿到后者只有两条路：真芯片，或者**让 FPGA 自己扮从机**（自环）。
自环的时序是真的（27 MHz 真分频、真开漏争用），但从机响应是模型——这一点不能含糊。
