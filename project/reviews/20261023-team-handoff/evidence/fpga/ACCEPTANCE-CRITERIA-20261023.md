## §6 回归基线（"防止功能丢失"的核心机制）

### 6.1 为什么需要

**7 个功能开关全关，从来没有一次"全开"的构建。** 这意味着：
- 每个功能单独写对了（有 tb），但**它们从没一起跑过**
- 一旦打开某个开关，可能触发从未见过的交互

### 6.2 基线定义

每次改动前，先固定一份"黄金码流"：

```bash
python build_product.py golden_<date> full 1
sha256sum golden_<date>/impl/pnr/board.fs > golden_<date>.sha256
```

### 6.3 三条比对规则

| 场景 | 要求 |
|---|---|
| 开关关闭时 | **码流逐字节相同**（哈希一致）。不一致 ⇒ 必须逐条解释差异来源 |
| 开关打开时 | 该功能相关的 tb 全绿；**其余 tb 仍全绿** |
| 任何改动 | `run_sims.py` 的用例数不得减少 |

### 6.4 新增功能的标准流程（六步）

1. 参数默认 **关闭**
2. 关闭路径写成 `assign x = 0`，**不写 `if` 包住整个逻辑**（避免综合器行为不确定）
3. 写 tb，含**反向对照**（故意改坏，确认判据会红）
4. 关闭态跑回归 → 必须与基线哈希一致
5. 打开态跑回归 → 该功能 tb 绿，其余仍绿
6. 资源/时序进 R 红线内

**第 3 步的反向对照是必须的**：`tb_decay2` 的三个判据最初都没"牙"，是反向对照测出来的。
