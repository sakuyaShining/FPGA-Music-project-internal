## 三、要更正的两处（一处是我的错）

### 3.1 我说错了：「物理可达电极只有 7 路」

我前几轮反复讲过「`pad[5..13]`（32–40）不在排针上，物理可达电极只有 7 路（27/28/29/30/31/41/42）」。

**这是错的。** 官方 `Tang_nano_20K_LCD.cst` 明确把 27–42 连续 16 个脚分配给 RGB LCD 数据线：

```
IO_LOC "LCD_B[4]" 27;  ... LCD_B[0] 31;
IO_LOC "LCD_G[5]" 32;  ... LCD_G[0] 37;
IO_LOC "LCD_R[4]" 38;  ... LCD_R[0] 42;
IO_LOC "LCD_DEN" 48;   IO_LOC "LCD_CLK" 77;
```

Sipeed 的 4.3"/7" RGB LCD 模块就是**插在这 40-pin 排针上**的。不插屏时，**27–42 全部可用作电极输入**。

**所以 v1 的「16 电极直连」在物理上是成立的。** 我之前的说法把可行方案误判成不可行，需要撤回。

### 3.2 载板的「J6 pin N → FPGA pin M」这一层，从来没被验证过

我读了载板的 `hardware/current/interface-references/expected-pin-nets.json`：

```json
"J5": { "5": "SENSE_4", "6": "SENSE_3", "7": "I2S_BCK", "8": "I2S_DIN",
        "10": "SENSE_5", "11": "I2S_LRCK", "15": "GND", "16": "3V3_IO" },
"J6": { "5": "TP_INT", "6": "BUS_MOSI", ... }
```

这份表只记录「**连接器第几脚接什么网络**」，**不包含「这个脚对应 FPGA 几号」**。而那一层来自 `nano-header-candidate.csv`，它的 status 字段自己写着：

```
candidate_not_for_connection_until_board_and_wrapper_check
```

**从未验证过。**

而且它有硬冲突：csv 把 15–20 分配给 `BUS_MOSI` / `SCAN_LATCH` / `INPUT_LOAD_N` / `LCD_VIS_CS_N` / `LCD_HARM_CS_N` / `LCD_SHARED_DC`，但官方 `blink_leds.cst` 说 **15–20 是板载 6 个 LED**：

```
IO_LOC "leds[5]" 20;  ...  IO_LOC "leds[0]" 15;
```

csv 的 `existing_load` 列自己也写着 `onboard_LED_510ohm`——**它知道这些脚挂着 LED，却仍把它们当排针信号用。**

**两种可能，都要命**：

| 情况 | 后果 |
|---|---|
| 15–20 在排针上但并着 LED | 做输出 → LED 会跟着闪、驱动被 510 Ω 分流；做**电极输入 → 510 Ω+LED 形成弱上拉，会干扰 PULL_DOWN 放电计数** |
| 15–20 不在排针上 | 载板这 6 根线接在了空脚或别的信号上，**整块板的扫描链/屏接口全错位** |

**这条比 v1 的引脚表重要得多。** v1 的 `.cst` 用 27–42 做电极，干净避开了 15–20；**载板没避开。**

### 3.3 v1 和载板根本不是同一套输入方案

| | v1（这份码流） | 载板（`e098c5db`） |
|---|---|---|
| 电极输入 | **16 路直连** 27–42 | **6 路 `SENSE_0..5`** + 扫描链（6×4067 → 84 节点） |
| 扫描链 | 无 | `BUS_SCK` / `BUS_MOSI` / `SCAN_LATCH` / `INPUT_LOAD_N` / `BUS_RETURN` |
| 屏 | 无 | `HARM_CS_N` / `TP_INT` / `J10` 12P |
| I²C | 无 | `I2C_SDA` / `I2C_SCL` |
| AUX | 板载 54/55/56 直出 | 载板 `I2S_BCK/DIN/LRCK` 走排针 |

**结论：`impl_pnr_board.fs` 烧进 Nano 能出声，但插到载板上不会工作。** 载板需要的是 6 路 SENSE + 扫描链那套 RTL，v1 里没有。

| 项 | 评价 |

**这份文档的水平，比之前所有采购/BOM 文档都高一个档次。**

### 4.2 三个要留意的点

#### ① Verify Failed 的判定方式有残余风险

文档说「只要 program 阶段 100% 走完就视为成功」。但 **program 成功 + verify 失败，也可能是真没烧进去**（配置口被 SSPI 占用后，回读路径本身失效，所以 verify 失败不能区分「烧对了」和「没烧对」）。

文档给的替代验证是对的——`python tools/board_velocity_check.py dump` 读到 `0xD0 = 0x75`。**这一条应该升级为主判据，而不是补充说明。** 建议改成：

> **唯一判据**：串口读到 `0xD0=0x75`。verify 报错不作为成功或失败的依据。

#### ② 「上电静音」与「码流没烧进去」症状相同

`0x60 NOTE_NUM=0` ⇒ 上电静音（设计意图）；码流没烧进去 ⇒ 也无声。**两种情况的用户感受完全一样**，只能靠读寄存器区分。建议在 §7 第一行加一句：「先读 `0xD0`，再判断其他」。

#### ③ 时序数据与既有记录一致，但缺 PnR 报告原件

| 项 | 91 号文档 | 项目既有记录 | 一致性 |
|---|---|---|---|
| setup 违规 | 0 | — | — |
| hold 违规 | 0 | hold slack **+0.205 ns** | ✅ 正 slack = 0 违规 |
| 最差 slack | **+11.300 ns** | setup **+11.300 ns** | ✅ 完全一致 |
| 资源 | LUT 3,080 / Reg 4,302 / BSRAM 15 | BSRAM 15/46 | ✅ 一致 |

**说明这份 PnR 结果之前就登记过，不是新跑的。** 但文档没附 `impl_pnr_board.rpt.txt` 原件，建议补上——否则「+11.300 ns」无法被第三方复核。

## 五、v1 的真实定位

**它不是一个「产品版本」，是一条「可烧录基线」。**

| 维度 | v1 状态 |
|---|---|
| 工具链 | ✅ 通（Gowin EDA V1.9.11.03 → 综合 → PnR → 码流） |
| 综合/PnR | ✅ 通（64.4 s，LUT 3,080） |
| 时序 | ✅ 通（setup/hold 双 0 违规，+11.300 ns） |
| 码流 | ✅ 已生成（SHA256 可验） |
| 配置协议 | ✅ 通（沙盒式上传、CRC16-CCITT、7 种结果码） |
| 声音引擎 | ✅ 32 组 × 16 分量 |
| **实物验收** | ❌ **零**——未烧录、未上板、未测延迟 |
| 84 电极 MUX | ❌ 无模块 |
| J10 触控显示 | ❌ 无模块 |
| EEPROM | ❌ 无模块 |
| TF 录放 | ❌ 无模块 |

**它的价值恰恰在「实物验收为零」这一栏是诚实的。** 文档自己写了「不能跨栏借完成度」，这句话应该成为这个项目所有验收文档的模板。

| 文档 | 要改什么 | 优先级 |
|---|---|---|
| 我之前「物理可达电极 7 路」的说法 | **撤回**，改为「27–42 共 16 路，不插屏时全可用」 | 已改 |

### 6.3 唯一能定这件事的方法

- 导通 → csv 对，但 15–20 带 LED 负载，电极输入不能用
- 不导通 → csv 错，载板这 6 根线接错位置

**这个测量 5 分钟能做完，比任何文档推演都可靠。** 板子就在手上（v1 已能烧）。
